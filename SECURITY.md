# Безопасность

Как сообщить об уязвимости, что уже защищено в коде и CI и как обращаться с журналом и секретами. Стенд защищён от типовых атак на вход и API. В пилоте ключ подписи живёт в HSM или KMS банка, а КЭП проверяет СКЗИ банка.

## Нашли уязвимость

Пишите владельцу репозитория [@KonkovDV](https://github.com/KonkovDV). Укажите коммит `main`, шаги воспроизведения и оценку влияния; реальные персональные данные не прикладывайте. Пока исправления нет, деталей в открытых issue не публикуйте. Ответ — в течение трёх рабочих дней, исправление выходит в `main`.

Приватная форма GitHub используется, только если в настройках репозитория включён private vulnerability reporting. На 27.10.2026 он выключен: посторонний по ссылке [security/advisories/new](https://github.com/KonkovDV/Mandat/security/advisories/new) сообщение не отправит. Когда владелец его включит, форма станет основным каналом. Открытые issue для уязвимостей не используются ни до, ни после.

## Поддерживаемые версии

Релизов нет. Исправления выходят только в `main`. Веток поддержки старых версий нет: проверяйте уязвимость на последнем коммите `main`. Срок, до которого отдельная версия ещё получает исправления, не задан: такой версии нет.

## Что уже защищено

| Где | Как |
|---|---|
| Разбор XML | `defusedxml`: без DTD и внешних сущностей, с лимитами на размер, число элементов и глубину (`intake/xml_safety.py`) |
| Реквизиты | ИНН, ОГРН, СНИЛС и КПП принимаются только из цифр ASCII и только строкой: арабские или полноширинные цифры и число вместо строки отвергаются |
| Каталог кейса | путь документа не выходит за каталог кейса (тест `test_case_loader_blocks_path_traversal`) |
| Вход в API | без токенов ответ 503, с неверным 401. Токены пользователей хранятся только хешем SHA-256 (`MANDAT_API_USERS`), сравнение за постоянное время. Рядом со списком пользователей общий `MANDAT_API_TOKEN` не действует |
| Роли и владельцы | `operator` и `reviewer` видят только свои кейсы, `auditor` читает всё и ничего не пишет, `admin` видит все кейсы, создаёт кейсы и события, но решений разбора не принимает. Чужой кейс отвечает 404. `case_id` в режиме пользователей выдаёт сервер |
| Нагрузка на API | тело запроса до 8 МБ, хранится не больше 1000 отчётов (в памяти, SQLite или Redis, `MANDAT_API_STORE`), 120 запросов в минуту с адреса соединения (`MANDAT_API_RATE_PER_MIN`). `X-Forwarded-For` не читается, за прокси лимит ставится на прокси |
| Перезапись кейса | повтор `case_id` даёт 409, перезапись только явно, через `replace=true` |
| Swagger | `/docs` и `/openapi.json` выключены, пока не задан `MANDAT_API_DOCS=1` |
| HTML-отчёт | все данные кейса экранируются, отчёт отдаётся с CSP `default-src 'none'` |
| Локальная модель | хосты из `MANDAT_LLM_ALLOWED_HOSTS`; в pilot/prod — только `https` (исключение: `http://127.0.0.1\|localhost` при `MANDAT_LLM_ALLOW_INSECURE_LOOPBACK=1`); без redirect, proxy-env игнорируется; перед отправкой ФИО заменяются метками, реквизиты псевдонимизируются ([защита данных](docs/DATA_PROTECTION.md)). Egress/mTLS/DNS — ops-контроль банка, не заменяется allowlist |
| Журнал решений | хеш-цепочка, HMAC, файл-свидетель последней записи, дерево Меркла для доказательства включения. По настройке `MANDAT_JOURNAL_ANCHOR` хеш закрытого сегмента уходит во внешний якорь: файл на другом томе, вебхук со сверкой у получателя, метка времени RFC 3161 с проверкой цепочки и отзыва сертификата, Sigstore Rekor v1 и v2. С файлом состояния Rekor проверяется доказательство согласованности, с заданными свидетелями — их подписи |
| Удостоверения | подпись Ed25519, подменённый список статусов при проверке отвергается. Индексы в списке случайные, список не меньше 131 072 бит, короткий список или индекс за его границей отвергаются |
| Ключ подписи | `MANDAT_SIGNER`: файл PEM (в `pilot` и `prod` только зашифрованный фразой), HSM по PKCS#11, Vault Transit или AWS KMS. Каждая подпись до выпуска проверяется открытым ключом подписанта. Связка ключей различает действующий, выведенный и скомпрометированный ключ ([ключи](docs/KEYS.md#подписант-удостоверений)) |
| Контейнер | непривилегированный пользователь, `read_only`, `no-new-privileges`, порт только на `127.0.0.1` |
| Внешний JSON | `strictjson` по I-JSON (RFC 7493): повтор ключа, NaN, бесконечность, число вне IEEE 754, одиночный суррогат и глубина больше 64 — ошибка входа. Так читаются тела трёх POST (в API это 422), манифест кейса, выписка ЕГРЮЛ, ответ модели, удостоверение, списки статусов, журнал, список пользователей и импорт классификатора. Не-символы вроде U+FFFE остаются: каноническая запись пишет их однозначно, а тот же разбор читает журнал. Ответ read-back якоря читается обычным `json.loads`: слишком глубокий документ роняет проверку, а не даёт отказ ([#131](https://github.com/KonkovDV/Mandat/issues/131)) |
| Допуск операции | `authorize_operation` сверяет организацию, день операции по Москве, операцию, сумму, представителя, получателя и одноразовый `nonce` (C-18). HTTP-маршрута допуска нет ([#100](https://github.com/KonkovDV/Mandat/issues/100)). На стенде вызов без запроса привязку не проверяет; в `pilot` и `prod` без запроса — отказ |
| Подпись событий | [Standard Webhooks 1.0](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md): HMAC-SHA256 над `id.timestamp.body`, секрет `whsec_` от 24 до 64 байт или ключ Ed25519 `whsk_` (подпись `v1a`), несколько подписей в заголовке для смены ключа без простоя, окно ±5 минут, метка времени — от 1 до 12 цифр, повтор `webhook-id` отвергается при переданном хранилище. В `pilot` и `prod` без хранилища повторов событие отклоняется. Проверено на тестовом векторе эталонной библиотеки |
| CI и цепочка поставки | у токена по умолчанию нет прав, каждой задаче выдаются только нужные. Все действия закреплены полными хешами коммитов с версией в комментарии, базовый образ — по дайджесту. `pip-audit` на каждом прогоне, статический анализ CodeQL на PR в `main` и раз в неделю, Dependabot для действий, pip и Docker, OpenSSF Scorecard раз в неделю. Для `main` собираются пакет и CycloneDX SBOM, к ним выпускаются подписанные аттестации происхождения (SLSA provenance) и SBOM. Как проверить артефакт — [ниже](#проверить-пакет) |

## Проверить пакет

Артефакт `dist` собирается только при push в `main` и хранится 30 дней. Релизов на GitHub нет: подпись относится к этому артефакту, а не к странице Releases. Локальная сборка из исходников эту подпись не получает ([как собрать](CONTRIBUTING.md#сборка-пакета)).

В артефакте три файла: колесо `mandat-<версия>-py3-none-any.whl`, sdist `mandat-<версия>.tar.gz` и `mandat.cdx.json` (SBOM CycloneDX). Версия — из `pyproject.toml`, сейчас 0.3.0. Происхождение SLSA (предикат `https://slsa.dev/provenance/v1`) покрывает колесо и sdist. Аттестация SBOM (предикат `https://cyclonedx.org/bom`) покрывает колесо.

Ожидаемая подпись сборки — рабочий процесс `https://github.com/KonkovDV/Mandat/.github/workflows/ci.yml` на `refs/heads/main`.

```bash
gh run download <id> -n dist -D dist
gh attestation verify dist/mandat-0.3.0-py3-none-any.whl --repo KonkovDV/Mandat --signer-workflow KonkovDV/Mandat/.github/workflows/ci.yml --source-ref refs/heads/main
gh attestation verify dist/mandat-0.3.0-py3-none-any.whl --repo KonkovDV/Mandat --predicate-type https://cyclonedx.org/bom
```

Команды проверены 27.10.2026 на колесе из артефакта прогона [40456329213](https://github.com/KonkovDV/Mandat/actions/runs/40456329213) (коммит `1c61c24`): обе завершились с кодом 0. Чужой `--source-ref` и файл с изменённым байтом дают код 1: у изменённого файла аттестации нет. Та же проверка происхождения применяется к sdist: в аттестации он указан рядом с колесом.

## Зависимости и сканеры

**Выбор.** У ядра две зависимости: `defusedxml` и `cryptography`. Новая зависимость ядра добавляется только с обоснованием в PR.

**Получение.** Ставятся lock-файлы с хешами (`uv pip compile --generate-hashes`, [requirements/README.md](requirements/README.md)). Сборочный бэкенд — `requirements/build.lock`, сборка идёт с `--no-isolation`, чтобы pip не скачал бэкенд без хеша. Базовый образ контейнера закреплён дайджестом.

**Учёт.** Dependabot раз в неделю: действия GitHub одной группой, pip, Docker и npm в `submission/deck`. Для `main` к артефакту прилагается SBOM CycloneDX. PR Dependabot по pip не двигает lock-файлы сам: их пересобирают до влития ([requirements/README.md](requirements/README.md#dependabot)).

**Порог.** Находка не помечается как неэксплуатируемая: списка подавлений нет. Единственное послабление — Trivy не валит сборку на уязвимости, для которых исправления ещё нет.

| Проверка | Порог | Что блокирует |
|---|---|---|
| pip-audit | любая известная уязвимость в снимке окружения тестов и в `runtime.lock` | задача `test`, она обязательна для Python 3.11–3.13 |
| Trivy | CRITICAL и HIGH, для которых есть исправление (`ignore-unfixed`) | задача `docker`, она обязательна |
| ruff, правила `S` | срабатывание блокирует; глобально пропущен `S101`, в `tests` пропущены `S` и `B`, в `scripts` — `S603` и `S607` | задача `test` |
| CodeQL | отчёт на PR в `main` и по понедельникам | ничего: задача `analyze` не входит в обязательные проверки |

Лицензии зависимостей отдельным порогом не заданы: pip-audit смотрит уязвимости, не лицензии. Если pip-audit красный, пакет поднимают через `uv pip compile --upgrade-package` и обновляют lock. Проверку не отключают.

## Настройки репозитория

Снято с API репозитория 27.10.2026.

- Secret scanning и push protection включены. Dependabot security updates выключены: версии двигает еженедельный Dependabot и пересборка lock-файлов.
- Private vulnerability reporting выключен. Куда писать — [выше](#нашли-уязвимость).
- Защита `main` требует свежие проверки (`strict`): `analysis` (OpenSSF Scorecard), `docker`, `package`, `test (3.11)`, `test (3.12)`, `test (3.13)`. Не обязательны `test (3.14)`, `redis`, `compose-pilot` и CodeQL `analyze`. Задача `package` запускается только при push в `main`, на PR её нет: пакет собирается после влития.
- Обязательного ревью нет. Правило не распространяется на администраторов: администратор может влить изменение в обход проверок. Force-push и удаление ветки `main` запрещены.

## Журнал и внешний якорь

На стенде (`MANDAT_ENV=demo`, значение по умолчанию) журнал можно вести без ключа. При `MANDAT_ENV=pilot` или `prod` без `MANDAT_JOURNAL_KEY` запись в журнал не делается и CLI завершается с понятной ошибкой.

Хеш-цепочка и свидетель не спасут, если злоумышленник может переписать оба файла. Поэтому хеш каждого закрытого сегмента можно публиковать вне машины. Приёмники задаёт `MANDAT_JOURNAL_ANCHOR`: файл на другом томе, вебхук, метка времени RFC 3161 или Sigstore Rekor. С заданными приёмниками `mandat journal-verify` требует квитанцию на каждый закрытый сегмент и перепроверяет её у приёмника. В `pilot` и `prod` без якоря сервис пишет предупреждение, а с `MANDAT_JOURNAL_ANCHOR_POLICY=fail` не стартует. Настройка приёмников — в [модели ключей](docs/KEYS.md#внешний-якорь-журнала).

Корень Меркла можно сверять и вручную, например с копией в СЭД или SIEM банка:

```bash
mandat journal-verify var/demo/journal.jsonl            # печатает merkle_root
mandat journal-verify var/demo/journal.jsonl --merkle-anchor <сохранённый корень>
```

Если корень не совпал, команда возвращает код 1.

## Секреты

`MANDAT_API_TOKEN`, токены из `mandat api-user`, `MANDAT_JOURNAL_KEY`, `MANDAT_PII_KEY` и ключ подписи удостоверений в репозиторий не кладутся. Образец без значений лежит в `.env.example`, сам `.env` в `.gitignore`. Ключи, которые создаёт `mandat demo`, годятся только для стенда.

Файлы ключей пишутся во временный файл того же каталога с правами 0600 в двоичном режиме, сбрасываются на диск и публикуются жёсткой ссылкой: читатель не увидит недописанный ключ, существующий ключ не перезаписывается. Ключ, открытый группе или всем (права шире 0600), не читается: команда просит `chmod 600`. В Windows права POSIX не действуют: доступ к каталогу ключей ограничивают средствами ОС (ACL). Для пилота ключи должны жить в KMS или HSM банка.
