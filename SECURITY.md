# Безопасность

Как сообщить об уязвимости, что уже защищено в коде и CI и как обращаться с журналом и секретами. Стенд защищён от типовых атак на вход и API. В пилоте ключ подписи живёт в HSM или KMS банка, а КЭП проверяет СКЗИ банка.

## Нашли уязвимость

Пишите владельцу репозитория [@KonkovDV](https://github.com/KonkovDV). Укажите коммит `main`, шаги воспроизведения и оценку влияния; реальные персональные данные не прикладывайте. Пока исправления нет, деталей в открытых issue не публикуйте. Ответ — в течение трёх рабочих дней, исправление выходит в `main`.

Приватная форма GitHub используется, только если в настройках репозитория включён private vulnerability reporting. На 27.10.2026 он выключен: посторонний по ссылке [security/advisories/new](https://github.com/KonkovDV/Mandat/security/advisories/new) сообщение не отправит. Когда владелец его включит, форма станет основным каналом. Открытые issue для уязвимостей не используются ни до, ни после.

## Поддерживаемые версии

Поддерживается последний релиз и `main`. Исправления выходят в `main` и в следующем релизе; веток поддержки старых версий нет, поэтому уязвимость проверяйте на последнем коммите `main`.

## Что уже защищено

| Где | Как |
|---|---|
| Разбор XML | `defusedxml`: без DTD и внешних сущностей, с лимитами на размер, число элементов и глубину (`intake/xml_safety.py`) |
| Реквизиты | ИНН, ОГРН, СНИЛС и КПП принимаются только из цифр ASCII и только строкой: арабские или полноширинные цифры и число вместо строки отвергаются |
| Каталог кейса | путь документа не выходит за каталог кейса (тест `test_case_loader_blocks_path_traversal`) |
| Вход в API | без токенов ответ 503, с неверным 401. Токены пользователей хранятся только хешем SHA-256 (`MANDAT_API_USERS`), сравнение за постоянное время. Рядом со списком пользователей общий `MANDAT_API_TOKEN` не действует |
| Роли и владельцы | `operator` и `reviewer` видят только свои кейсы, `auditor` читает всё и ничего не пишет, `admin` видит все кейсы, создаёт кейсы и события, но решений разбора не принимает. `dbo` — учётная запись системы банка: только допуск операции для своих `audiences`, в `pilot` и `prod` допуск выдаётся только ей. Чужой кейс отвечает 404. `case_id` в режиме пользователей выдаёт сервер |
| Нагрузка на API | тело запроса до 8 МБ, хранится не больше 1000 отчётов на пользователя (в памяти, SQLite или Redis, `MANDAT_API_STORE`), 120 запросов в минуту с адреса соединения (`MANDAT_API_RATE_PER_MIN`). `X-Forwarded-For` не читается, за прокси лимит ставится на прокси |
| Перезапись кейса | повтор `case_id` даёт 409, перезапись только явно, через `replace=true` |
| Swagger | `/docs` и `/openapi.json` выключены, включает их `MANDAT_API_DOCS=1` |
| HTML-отчёт | все данные кейса экранируются, отчёт отдаётся с CSP `default-src 'none'` |
| Локальная модель | хосты из `MANDAT_LLM_ALLOWED_HOSTS`; в pilot/prod — только `https` (исключение: `http://127.0.0.1\|localhost` при `MANDAT_LLM_ALLOW_INSECURE_LOOPBACK=1`); без перенаправлений, переменные прокси игнорируются; перед отправкой ФИО заменяются метками, реквизиты псевдонимизируются ([защита данных](docs/DATA_PROTECTION.md)). Исходящий трафик, mTLS (взаимную проверку сертификатов) и DNS контролирует сеть банка, список разрешённых хостов их дополняет |
| Журнал решений | хеш-цепочка, HMAC, файл-свидетель последней записи, дерево Меркла для доказательства включения. По настройке `MANDAT_JOURNAL_ANCHOR` хеш закрытого сегмента уходит во внешний якорь: файл на другом томе, вебхук со сверкой у получателя, метка времени RFC 3161 с проверкой цепочки и отзыва сертификата, Sigstore Rekor v1 и v2. С файлом состояния Rekor проверяется доказательство согласованности, с заданными свидетелями — их подписи |
| Удостоверения | подпись Ed25519, подменённый список статусов при проверке отвергается. Индексы в списке случайные, список не меньше 131 072 бит, короткий список или индекс за его границей отвергаются |
| Ключ подписи | `MANDAT_SIGNER`: файл PEM (в `pilot` и `prod` только зашифрованный фразой), HSM по PKCS#11, Vault Transit или AWS KMS. Каждая подпись до выпуска проверяется открытым ключом подписанта. Связка ключей различает действующий, выведенный и скомпрометированный ключ ([ключи](docs/KEYS.md#подписант-удостоверений)) |
| Ключи журнала, ПДн и хранилища | в `pilot` и `prod` — только случайные: не меньше 32 байт в hex или base64; пароли, повторы и короткие ключи сервис не принимает, потому что HMAC и HKDF перебор не замедляют ([KEYS.md](docs/KEYS.md)) |
| Текст клиента | разбор и маскировка — за линейное время: поиск адресов почты идёт от каждого «@», маска журнала сервера режет текст до маски; мониторинг — скользящим окном и по индексам, ответ до 1 000 000 связей «тревога — право» |
| Контейнер | непривилегированный пользователь, `read_only`, `no-new-privileges`, порт только на `127.0.0.1` |
| Журнал аудита | ПДн клиентов в нём нет: свободный текст сотрудника (основание решения разбора) уходит отпечатком HMAC на ключе журнала, текст живёт в истории разбора и удаляется с кейсом |
| Заголовки ответа | присланный `X-Request-ID` возвращается, только если он из безопасного алфавита, а в журнал сервера попадает через маску номеров; на 401 — `WWW-Authenticate: Bearer` по RFC 6750 |
| Восстановление из копии | `mandat restore-check` сверяет восстановленное хранилище и списки статусов с журналом: удалённый по 152-ФЗ кейс не возвращается, отзыв удостоверения не откатывается (C-24) |
| Внешний JSON | `strictjson` по I-JSON (RFC 7493): повтор ключа, NaN, бесконечность, число вне IEEE 754, одиночный суррогат и глубина больше 64 — ошибка входа. Так читаются тела POST (в API это 422, на путях AuthZEN — 400 по разделу 10.1.2 спецификации), манифест кейса, выписка ЕГРЮЛ, ответ модели, удостоверение, списки статусов, журнал, список пользователей и импорт классификатора. Не-символы вроде U+FFFE остаются: каноническая запись пишет их однозначно, а тот же разбор читает журнал. Ответ read-back якоря тоже читается строго и не длиннее 1 МБ: слишком глубокий документ — отказ, а не падение проверки |
| Допуск операции | `authorize_operation` сверяет организацию, день операции по Москве, операцию, сумму, представителя, получателя и одноразовый `nonce` (C-18). HTTP-маршруты — `POST /v1/operations/authorize` и по OpenID AuthZEN 1.0 `/access/v1/evaluation` и `/access/v1/evaluations` (C-23): в `pilot` и `prod` допуск получает только учётная запись `dbo` для своих `audiences`, ошибка запроса `nonce` не расходует. На стенде вызов функции без запроса привязку не проверяет; в `pilot` и `prod` без запроса — отказ |
| Подпись событий | [Standard Webhooks 1.0](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md): HMAC-SHA256 над `id.timestamp.body`, секрет `whsec_` от 24 до 64 байт или ключ Ed25519 `whsk_` (подпись `v1a`), несколько подписей в заголовке для смены ключа без простоя, окно ±5 минут, метка времени — от 1 до 12 цифр, повтор `webhook-id` отвергается при переданном хранилище. В `pilot` и `prod` без хранилища повторов событие отклоняется. Проверено на тестовом векторе эталонной библиотеки |
| CI и цепочка поставки | у токена по умолчанию нет прав, каждой задаче выдаются только нужные. Все действия закреплены полными хешами коммитов с версией в комментарии, базовый образ — по дайджесту. `pip-audit` на каждом прогоне, статический анализ CodeQL на PR в `main` и раз в неделю, OpenSSF Scorecard раз в неделю, фаззинг разбора входа в ClusterFuzzLite на PR и раз в неделю. Для `main` собираются пакет и CycloneDX SBOM с подписанными аттестациями происхождения (SLSA provenance) и SBOM. Каждый файл релиза подписан Sigstore, образ контейнера публикуется в GHCR со своей аттестацией. Как проверить — [ниже](#проверить-пакет) |

## Проверить пакет

Релиз выпускает рабочий процесс `release.yml` по номеру версии из `pyproject.toml`. В релизе колесо, sdist, SBOM CycloneDX, презентация и пакет аналитики; у каждого файла рядом подпись Sigstore (`*.sigstore.json`), происхождение сборки SLSA лежит в `mandat-<версия>.intoto.jsonl` и в аттестациях GitHub. Образ `ghcr.io/konkovdv/mandat:<версия>` несёт свою аттестацию.

```bash
gh release download v0.4.0 --repo KonkovDV/Mandat -D release
gh attestation verify release/mandat-0.4.0-py3-none-any.whl --repo KonkovDV/Mandat --signer-workflow KonkovDV/Mandat/.github/workflows/release.yml
gh attestation verify oci://ghcr.io/konkovdv/mandat:0.4.0 --repo KonkovDV/Mandat
python -m sigstore verify github release/Mandat_VTB-0.4.0.pdf --repository KonkovDV/Mandat --name release --trigger workflow_dispatch
```

Проверено 22.11.2026 на файлах релиза 0.4.0: колесо и презентация проходят `sigstore verify` с привязкой к репозиторию, процессу `release` и ветке `main`, а презентация с одним добавленным байтом не проходит. В `mandat-0.4.0.intoto.jsonl` — конверт DSSE с выпиской SLSA provenance v1 на все шесть файлов.

Кроме релизов, артефакт `dist` собирается при каждом push в `main` и хранится 30 дней. Локальная сборка из исходников подписи не получает ([как собрать](CONTRIBUTING.md#сборка-пакета)).

В артефакте три файла: колесо `mandat-<версия>-py3-none-any.whl`, sdist `mandat-<версия>.tar.gz` и `mandat.cdx.json` (SBOM CycloneDX). Версия — из `pyproject.toml`, сейчас 0.4.0. Происхождение SLSA (предикат `https://slsa.dev/provenance/v1`) покрывает колесо и sdist. Аттестация SBOM (предикат `https://cyclonedx.org/bom`) покрывает колесо.

Ожидаемая подпись сборки — рабочий процесс `https://github.com/KonkovDV/Mandat/.github/workflows/ci.yml` на `refs/heads/main`.

```bash
gh run download <id> -n dist -D dist
gh attestation verify dist/mandat-0.4.0-py3-none-any.whl --repo KonkovDV/Mandat --signer-workflow KonkovDV/Mandat/.github/workflows/ci.yml --source-ref refs/heads/main
gh attestation verify dist/mandat-0.4.0-py3-none-any.whl --repo KonkovDV/Mandat --predicate-type https://cyclonedx.org/bom
```

Команды проверены 27.10.2026 на колесе из артефакта `main`: обе завершились с кодом 0. Чужой `--source-ref` и файл с изменённым байтом дают код 1: у изменённого файла аттестации нет. Та же проверка происхождения применяется к sdist: в аттестации он указан рядом с колесом.

## Зависимости и сканеры

**Выбор.** У ядра две зависимости: `defusedxml` и `cryptography`. Новая зависимость ядра добавляется только с обоснованием в PR.

**Получение.** Ставятся lock-файлы с хешами (`uv pip compile --generate-hashes`, [requirements/README.md](requirements/README.md)). Сборочный бэкенд — `requirements/build.lock`, сборка идёт с `--no-isolation`, чтобы pip не скачал бэкенд без хеша. Базовый образ контейнера закреплён дайджестом.

**Учёт.** Версии поднимаются вручную: lock-файлы пересобираются вместе с тестами ([requirements/README.md](requirements/README.md#обновление-версий)), а `pip-audit`, Trivy и `npm audit` на каждом PR и по расписанию сообщают, что пора. Dependabot настроен только на уязвимости: плановых PR с новыми версиями он не открывает (`open-pull-requests-limit: 0` в `.github/dependabot.yml`). Для `main` и релизов к пакету прилагается SBOM CycloneDX.

**Порог.** Находка не помечается как неэксплуатируемая: списка подавлений нет. Единственное послабление — Trivy не валит сборку на уязвимости, для которых исправления ещё нет.

| Проверка | Порог | Что блокирует |
|---|---|---|
| pip-audit | любая известная уязвимость в снимке окружения тестов и в `runtime.lock` | задача `test`, она обязательна для Python 3.11–3.13 |
| Trivy | CRITICAL и HIGH, для которых есть исправление (`ignore-unfixed`) | задача `docker`, она обязательна |

Обе проверки идут на каждом push и PR, а на `main` ещё и по расписанию, по понедельникам и четвергам: новая консультация появляется без изменения кода, и красный прогон по расписанию виден до следующего PR.
| ruff, правила `S` | срабатывание блокирует; глобально пропущен `S101`, в `tests` пропущены `S` и `B`, в `scripts` — `S603` и `S607` | задача `test` |
| CodeQL | отчёт на PR в `main` и по понедельникам | ничего: задача `analyze` не входит в обязательные проверки |
| ClusterFuzzLite, цели `fuzz/fuzz_*.py` | любое исключение, кроме объявленных отказов разбора, и зависание; на PR 5 минут по целям, которые задевает изменение, по понедельникам 30 минут по всем | задача `pr` рабочего процесса `cflite` на PR, в обязательные проверки не входит |
| gitleaks 8.30.1 (бинарник по SHA-256) | любая находка во всей истории git; найденное значение в лог не попадает (`--redact`) | ничего: задача `secret-scan` идёт на push, PR и по вторникам, но в обязательные проверки не входит |

Исключения gitleaks в `.gitleaks.toml` — не подавленные находки, а совпадения, которые секретом не являются: аннотации типов `key: Ed25519PrivateKey`, опубликованный тестовый вектор W3C vc-di-eddsa и пример из спецификации Standard Webhooks. У каждого — объяснение; новое добавляется только так же. Исключение по шаблону действует на само совпадение, а не на всю строку: токен, дописанный в строку с аннотацией, проверка ловит. В отличие от secret scanning GitHub, эта проверка переносится в контур банка: GitLab или Gitea запускают тот же бинарник с тем же файлом.

Лицензии зависимостей отдельным порогом не заданы: pip-audit смотрит уязвимости, не лицензии. Если pip-audit красный, пакет поднимают через `uv pip compile --upgrade-package` и обновляют lock. Проверку не отключают.

## Настройки репозитория

Что должно быть включено в настройках GitHub. Сверять после любой смены владельца или переноса репозитория.

- Secret scanning и push protection включены. Dependabot alerts и security updates включены; плановых PR нет, их выключает `.github/dependabot.yml`.
- Private vulnerability reporting выключен. Куда писать — [выше](#нашли-уязвимость).
- Защита `main`: запрещены force-push и удаление ветки, перед влитием нужны свежие проверки (`strict`) `docker`, `test (3.11)`, `test (3.12)`, `test (3.13)` и `analysis` (OpenSSF Scorecard). Задача `package` идёт только при push в `main`, поэтому в обязательные её не включают.
- Изменения идут через PR с одобрением второго участника команды: это учитывает проверка Code-Review в OpenSSF Scorecard.
- Pages публикуются из GitHub Actions, переменная `PAGES_ENABLED` = `true`.

## Журнал и внешний якорь

На стенде (`MANDAT_ENV=demo`, значение по умолчанию) журнал можно вести без ключа. При `MANDAT_ENV=pilot` или `prod` без `MANDAT_JOURNAL_KEY` запись в журнал не делается и CLI завершается с понятной ошибкой.

Хеш-цепочка и свидетель не спасут, если злоумышленник может переписать оба файла. Поэтому хеш каждого закрытого сегмента можно публиковать вне машины. Приёмники задаёт `MANDAT_JOURNAL_ANCHOR`: файл на другом томе, вебхук, метка времени RFC 3161 или Sigstore Rekor. С заданными приёмниками `mandat journal-verify` требует квитанцию на каждый закрытый сегмент и перепроверяет её у приёмника. В `pilot` и `prod` без якоря сервис пишет предупреждение, а с `MANDAT_JOURNAL_ANCHOR_POLICY=fail` не стартует; пилотный compose ставит `fail` по умолчанию. Настройка приёмников — в [модели ключей](docs/KEYS.md#внешний-якорь-журнала).

Корень Меркла можно сверять и вручную, например с копией в СЭД или SIEM банка:

```bash
mandat journal-verify var/demo/journal.jsonl            # печатает merkle_root
mandat journal-verify var/demo/journal.jsonl --merkle-anchor <сохранённый корень>
```

Если корень не совпал, команда возвращает код 1.

## Секреты

`MANDAT_API_TOKEN`, токены из `mandat api-user`, `MANDAT_JOURNAL_KEY`, `MANDAT_PII_KEY` и ключ подписи удостоверений в репозиторий не кладутся. Образец без значений лежит в `.env.example`, сам `.env` в `.gitignore`. Ключи, которые создаёт `mandat demo`, годятся только для стенда.

Файлы ключей пишутся во временный файл того же каталога с правами 0600 в двоичном режиме, сбрасываются на диск и публикуются жёсткой ссылкой: читатель не увидит недописанный ключ, существующий ключ не перезаписывается. Ключ, открытый группе или всем (права шире 0600), не читается: команда просит `chmod 600`. В Windows права POSIX не действуют: доступ к каталогу ключей ограничивают средствами ОС (ACL). Для пилота ключи должны жить в KMS или HSM банка.

Команды `mandat api-user` и `mandat webhook-secret` печатают новый секрет ровно один раз: в этом их назначение. Сервис хранит только SHA-256 токена (`token_sha256`), а секрет вебхука получает из окружения. CodeQL отмечает такой вывод как «чувствительные данные открытым текстом»; эти срабатывания ожидаемы и закрываются в GitHub как «Won't fix» с этим обоснованием. Чтобы секрет не остался в истории терминала, логах CI и записях сессии, на пилоте и в эксплуатации команды запускаются на рабочем месте администратора, а вывод сразу перенаправляется в хранилище секретов банка. Токен живёт не дольше 366 дней, в защищённом режиме срок обязателен; его можно отозвать полем `revoked`, утёкший токен заменяется новым.

Подробнее об угрозах: [модель угроз](docs/THREAT_MODEL.md), [границы доверия](docs/TRUST_BOUNDARIES.md).
