# Нагрузочный прогон API, 14.10.2026

Стенд: одна виртуальная машина, 8 vCPU, 16 ГБ ОЗУ, Python 3.13, один процесс uvicorn (`mandat serve`), loopback. Клиент `tools/load/run_load.py` (asyncio + httpx) на той же машине. Цикл одного запроса: `POST /v1/cases` (разбор МЧД, ЕГРЮЛ, устава и 39 правил) + `GET /v1/cases/{id}`. Журнал решений включён (`MANDAT_API_JOURNAL`), `MANDAT_ENV=demo`, лимит запросов снят, кроме фазы перегрузки.

**Честные границы.** Клиент и сервер делят CPU, сеть не участвует, один воркер, синтетические кейсы. Это сравнение версий и поиск узких мест, а не SLA и не прогноз для контура банка.

## Узкое место, найденное и исправленное (R2-PERF-1)

До исправления каждая запись журнала под блокировкой перечитывала весь файл, пересчитывала цепочку хешей всех записей и переписывала файл целиком: стоимость записи росла линейно, суммарная — квадратично. Под 16+ клиентами блокировка ждала дольше 5 с, и API отвечал 503.

Исправление (`audit/journal.py`): дозапись `O_APPEND` + `fsync`; полная проверка цепочки — только если байты файла или свидетель изменились с последней проверки этим процессом (сверка по SHA-256 содержимого, а не по mtime). Подделка между записями по-прежнему ловится (`tests/test_r2_races.py`).

## RedisStore (раунд R3)

Redis 8.0.2 на той же машине (`redis-server --save "" --appendonly no`), redis-py 8.1.0, 8 vCPU.
Команда: `python tools/load/run_load.py --store redis://127.0.0.1:6379/0 --workers N --stages 1,4,16,32,64 --soak-seconds 180 --overload`.

**Найдено и исправлено:**

- **R3-LOAD-1 (стенд).** При 64 клиентах сервер переставал отвечать совсем, все запросы — таймаут 30 с. `py-spy dump`: главный поток стоит в `logging.emit` — стенд отдавал stderr сервера в `PIPE` и не читал его, предупреждения uvicorn о `limit_concurrency` заполнили 64 КБ. Журнал сервера теперь пишется в файл. В проде то же случится с любым непрочитанным stderr — логи должен забирать сборщик (docker, journald).
- **R3-PERF-3.** С `--workers 4` один клиент получал 10 RPS при p50 96 мс вместо ~100 RPS при 9 мс; GET по keep-alive — 42 мс. Причина: uvicorn сам создаёт слушающий сокет с `proto=0`, и asyncio не включает TCP_NODELAY; заголовки и тело уходят двумя сегментами, второй ждёт delayed ACK. Исправлено протоколом `mandat.api.nodelay:NoDelayH11Protocol`.
- **R3-PERF-4.** С `--workers 4` запись соседнего процесса сбрасывала кэш хвоста журнала, и каждая запись проверяла журнал целиком: выдержка 24,5 → 17,3 RPS за 90 с. Теперь проверяются только новые записи (`journal._catch_up`).

## Что открыто

- **R2-PERF-2** — исправлено (сегменты, см. выше). Внешний якорь сегментов сделан в R3 (`audit/anchor.py`); его стоимость в нагрузке не мерялась (публикация раз в 1000 записей).
- Под 32+ клиентами редкие 503 из-за ожидания блокировки журнала (5 с): сервер ограничивает одновременные соединения (`MANDAT_API_MAX_CONCURRENCY`, по умолчанию 64), чтобы очередь не росла без предела.
- **R3-PERF-5** — исправлено манифестом сегментов (R4). Интервалы при 4 воркерах колеблются ±20 % без тренда — это шум общей машины (сервер, Redis и клиенты на одних 8 vCPU).
- Прогон на железе банка и Redis на отдельной машине (сетевая задержка) не выполнялись.
