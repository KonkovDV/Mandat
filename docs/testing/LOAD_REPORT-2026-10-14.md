# Нагрузочный прогон API, 14.10.2026

Стенд: одна виртуальная машина, 8 vCPU, 16 ГБ ОЗУ, Python 3.13, один процесс uvicorn (`mandat serve`), loopback. Клиент `tools/load/run_load.py` (asyncio + httpx) на той же машине. Цикл одного запроса: `POST /v1/cases` (разбор МЧД, ЕГРЮЛ, устава и 39 правил) + `GET /v1/cases/{id}`. Журнал решений включён (`MANDAT_API_JOURNAL`), `MANDAT_ENV=demo`, лимит запросов снят, кроме фазы перегрузки.

**Честные границы.** Клиент и сервер делят CPU, сеть не участвует, один воркер, синтетические кейсы. Это сравнение версий и поиск узких мест, а не SLA и не прогноз для контура банка.

## Узкое место, найденное и исправленное (R2-PERF-1)

До исправления каждая запись журнала под блокировкой перечитывала весь файл, пересчитывала цепочку хешей всех записей и переписывала файл целиком: стоимость записи росла линейно, суммарная — квадратично. Под 16+ клиентами блокировка ждала дольше 5 с, и API отвечал 503.

Исправление (`audit/journal.py`): дозапись `O_APPEND` + `fsync`; полная проверка цепочки — только если байты файла или свидетель изменились с последней проверки этим процессом (сверка по SHA-256 содержимого, а не по mtime). Подделка между записями по-прежнему ловится (`tests/test_r2_races.py`).

## После исправления

**Память (MemoryStore)** — таблица выше, столбцы «после». Насыщение около 140 RPS при 4 клиентах; дальше растёт только очередь (p95). Единичные 503 при 32–64 клиентах — ожидание блокировки журнала дольше 5 с.

**Перегрузка** (лимит 120 запросов в минуту с адреса, 16 клиентов, 5 с): 2829 запросов, 53 созданы, 2762 отсечены 429 с `Retry-After`, ошибок данных нет, p99 149 мс — отказ дешёвый.

**Выдержка** (8 клиентов, 180 с, память): 19 401 запись в журнале, ошибок 0, журнал цел. RSS сервера стабилен: 124–126 МБ (хранилище ограничено `MAX_REPORTS = 1000`), утечки не видно. RPS снижается со 151 до 75 по мере роста журнала: каждая запись всё ещё хеширует файл целиком (≈10 МБ к концу прогона). Это R2-PERF-2, исправлено — раздел ниже.

**Целостность.** После каждого прогона `verify_journal` — OK (5979, 4665 и 19 401 запись), повторов и потерь записей нет. Одновременные создания с одним `case_id` — один успех, остальные 409 (`tests/test_r2_races.py`).

Redis в окружении нет; прогон с `--store redis://…` не выполнялся.

## R2-PERF-2: сегменты журнала, выдержка после исправления

- Записей за прогон: 19 401 → 27 684. Журнал цел (`verify_journal` по всем сегментам), ошибок 0. RSS 120–121 МБ.
- RPS больше не падает с ростом журнала: интервалы 2–5 держатся на 146–148. Последний интервал на 9 % ниже. Причину я не установил: шум стенда или перечисление каталога с сегментами (≈28 файлов) — после одного прогона не разобрать.
- Пределы честно: одна машина, один процесс, `fsync` на каждую запись. Полная проверка журнала (`verify_journal`) остаётся O(n) — её делают аудит и CLI, а не запись.
- Сырые данные: `var/load-soak2.json` (до), `var/load-soak3.json` (после); в репозиторий не входят.

## Что открыто

- **R2-PERF-2** — исправлено (сегменты, см. выше). Остаётся внешний якорь хеша закрытого сегмента вне машины.
- Под 32+ клиентами редкие 503 из-за ожидания блокировки журнала (5 с): сервер ограничивает одновременные соединения (`MANDAT_API_MAX_CONCURRENCY`, по умолчанию 64), чтобы очередь не росла без предела.
- Многопроцессный прогон (`--workers N` с SQLite/Redis) и прогон на железе банка не выполнялись.
