# Спринт 2: доказательства по критериям и условиям трека

Записка для проверяющих решение № 2 (трек ВТБ «Финтех без границ», загрузка до 29.11.2026). По каждому из шести критериев: что сделано, чем это доказывается и где граница. По каждому из девяти условий трека: как оно выполнено. Числа о продукте — из `evidence.json` и [реестра утверждений](../CLAIMS_REGISTRY.md), у каждого есть команда воспроизведения. Критерии и условия — со страницы [fintechacademy.ru/task-1](https://fintechacademy.ru/task-1), прочитанной 23.11.2026; описаний к критериям организаторы не дали.

## Как проверить за десять минут

1. Открыть [страницу проекта](https://konkovdv.github.io/Mandat/): захват компании по шагам и проверка удостоверения работают прямо в браузере, без сервера.
2. Повторить сборку чисел: `make install`, затем `mandat demo`, `mandat showcase` и `python scripts/build_evidence.py --verify-source` — последняя команда подтверждает, что `evidence.json` собран из этих исходников.
3. Посмотреть зелёный CI на [последнем коммите](https://github.com/KonkovDV/Mandat/actions) и подписанный [релиз 0.4.0](https://github.com/KonkovDV/Mandat/releases/tag/v0.4.0).

## 1. Данные, безопасность и комплаенс (0–18)

Подход — защита по умолчанию и минимизация: данные клиента не покидают контур банка, в модель уходят метки, каждое действие с ПДн оставляет след, а соответствие проверяется по тексту норм, а не по пересказам.

| Требование | Что сделано | Доказательство | Граница |
|---|---|---|---|
| 115-ФЗ, ст. 7: идентифицировать представителя и получить сведения о документе-основании | это и есть задача продукта: полномочие проверяется на дату операции с полем документа и нормой | [нормы](DATA_PROTECTION_LAW.md#1-кто-оператор-и-на-каком-основании), [практика банков](BANK_PRACTICE.md) | основание обработки выбирает юрист банка |
| 152-ФЗ, ст. 5 и 18.1: минимизация, оценка вреда | ФИО, паспорт, СНИЛС и ИНН заменяются метками до модели; для акта оценки вреда по приказу Роскомнадзора № 178 разобраны все признаки перечня | `privacy/pii.py`, [оценка вреда](DATA_PROTECTION_LAW.md#оценка-вреда-раскладка-для-акта-банка) | акт оценки вреда — банк |
| 152-ФЗ, ст. 19 и 21: учёт действий, утечки, уничтожение | журнал с HMAC и деревом Меркла (RFC 9162) пишет создание, чтение, разбор, допуск и удаление кейса без самих данных; удаление по основанию закона с выгрузкой из журнала (приказ Роскомнадзора № 179) | `audit/journal.py`, `POST /v1/cases/{id}/erase`, C-09 | регламент реагирования — банк |
| Хранение | отчёты и разборы зашифрованы AES-256-GCM, шифр привязан к кейсу и владельцу: подменённая запись даёт отказ, а не чужие данные | `api/sealing.py`, [защита данных](DATA_PROTECTION.md) | шифр заменяется сертифицированным СКЗИ, если этого требует модель угроз банка |
| Ключи | в пилоте и эксплуатации — только случайные ключи не короче 32 байт; хранение в HSM, Vault или KMS | `audit/keymaterial.py`, [ключи](KEYS.md) | ГОСТ-подпись и КЭП — через СКЗИ банка |
| Разработка и цепочка поставки | зависимости из lock-файлов с хешами; pip-audit и Trivy на каждом PR и по расписанию; CodeQL, OpenSSF Scorecard, gitleaks по всей истории; SBOM CycloneDX и подписанное происхождение сборки; фаззинг разбора входа в ClusterFuzzLite | [SECURITY](../SECURITY.md), `.github/workflows/` | анализ уязвимостей по ОУД 4 для ПО переводов — вопрос к ИБ банка ([нормы](DATA_PROTECTION_LAW.md)) |
| Угрозы | модель угроз и шесть проходов аудита с ролями Red Team, ИБ, юриста и интегратора ДБО; найденное закрыто кодом и тестами | [модель угроз](THREAT_MODEL.md), [история изменений](../CHANGELOG.md) | тип угроз и уровень защищённости по ПП № 1119 определяет банк |

## 2. Техническая реализация, автоматизация и масштабирование (0–22)

**Архитектура.** Детерминированное ядро: 39 правил лежат данными, у каждого норма, поле документа и тест (C-01); четыре вердикта, и неизвестное не становится «да». Источники подключаются через порты: реестр МЧД, ЕГРЮЛ, ЕФРСБ, СКЗИ. HTTP API с ролями описан в [OpenAPI](api/openapi.json); ДБО получает допуск ровно на одну операцию с одноразовым `nonce` (C-18). ИИ советует, но не решает: вердикт выносят правила ([ADR-001](adr/ADR-001-verdict-ownership.md)).

**Автоматизация и качество.** CI на пяти версиях Python и на Windows, тесты хранилищ на настоящем Redis, нагрузочный прогон на каждом коммите. 2044 автотеста, покрытие 95,9 % (C-13); передоверие сверено со второй реализацией на Cedar; мутации входа фаззятся. Вся цепочка от проверки до отказа платежу после захвата — одной командой `mandat showcase` (C-22). Материалы сдачи собирает `make submission`.

**Масштабирование: расчёт мощности.** Замер 23.11.2026 стендом `tools/load/run_load.py`: полный цикл API «создать кейс и прочитать отчёт», то есть разбор, 39 правил, отчёт и запись в журнал. Машина — 4 vCPU Xeon 2,1 ГГц, клиент и сервер делят процессор, сеть — loopback, поэтому цифры занижены.

| Конфигурация | Клиентов | Запросов в секунду | p95 | Ошибки |
|---|---|---|---|---|
| один процесс, хранилище в памяти | 1 | 72,6 | 17 мс | 0 |
| один процесс, хранилище в памяти | 32 | 63,9 | 2,5 с | 2 из 533: один процесс перегружен |
| 4 воркера, SQLite | 8 | 119,5 | 222 мс | 0 |
| 4 воркера, SQLite | 32 | 95,6 | 1,1 с | 0 |

Повторить: `python tools/load/run_load.py --store sqlite --workers 4 --stages 8,32 --stage-seconds 8`.

Сколько нужно ВТБ. В финансовой модели от 180 до 450 тыс. событий с подписантами в год по сценариям (C-15). Даже 450 тыс. — это около 1 800 проверок в рабочий день, меньше одной в секунду в пиковый час. Один узел из замера держит больше сотни полных проверок в секунду, запас — два порядка. Поэтому второй узел нужен для надёжности, а не для мощности: воркеры не хранят состояния, `nonce`, статусы и журнал лежат в общем Redis, готовность узла показывает `/readyz`.

Чего замер не покрывает. Допуск платежа не перепроверяет кейс — он сверяет подпись удостоверения, его статус, пределы операции и одноразовый `nonce` (`services/admission.py`), но отдельно не замерялся. Его частота равна числу платежей представителей по МЧД, а такой цифры в открытых источниках нет: замер допуска — первая неделя пилота.

## 3. Оценка ценности: юнит-экономика, эффект и ROI (0–22)

Метод — модель затрат на формулах с тремя сценариями и явными допущениями ([экономика](ECONOMICS.md), [пакет аналитики](../submission/analytics/README.md)).

- Юнит-экономика одной проверки: вручную около 540 ₽, затраты банка на «Мандат» — около 69 ₽ с НДС на сопровождение (C-21).
- Базовый сценарий для ВТБ: 75 ставок и 140 млн ₽ предотвращённого ущерба в год, разовые затраты окупаются за 7,8 месяца (C-15, C-16).
- Чувствительность, NPV и IRR — в модели; лист «Банк» заново выводится независимым тестом (`tests/test_bank_model_independent.py`), модель сама проверяет 31 тождество.

Граница: доля клиентов с событием и минуты на кейс — допущения команды. Интервью подтвердили, что ручная сверка долгая, но чисел не дали ([интервью](discovery/INTERVIEWS.md)): их заменит хронометраж в пилоте.

## 5. Подтверждённость проблемы, ценности и рынка (0–12)

Проблема подтверждена пятью независимыми типами источников:

| Источник | Что подтверждает | Где |
|---|---|---|
| статистика Банка России за I–III кварталы 2026 года | у юрлиц операции без согласия крупнее средних в разы, возвращают мало | M-07, M-15, M-52 |
| судебная практика и громкие случаи | ошибка стоит денег в обе стороны: захват («ЭОС») и отказ законному руководителю (ВС РФ № 308-ЭС22-17199) | M-17, M-35 |
| регулирование в России и мире | проверка полномочия представителя — отдельная обязанность банка (115-ФЗ, FATF R10, AMLR ЕС) | [практика банков](BANK_PRACTICE.md) |
| рынок и аналоги | API МЧД отвечают про документ, а не про операцию; за рубежом «может ли подписать» уже продаётся | M-53–M-56, [конкуренты](COMPETITORS.md) |
| пять интервью с банками под NDA | подтвердились долгая ручная сверка, риск смены руководителя, невидимые события и интерес к пилоту | M-57, [интервью](discovery/INTERVIEWS.md) |

Граница: пять интервью — качественное подтверждение, а не выборка. Опрос клиентов МСБ готов, но не проведён.

## 6. Реалистичность пилота и готовность к внедрению (0–10)

Шестинедельный теневой пилот на одной операции — праве подписи платёжных документов по МЧД: «Мандат» проверяет те же пакеты, что и сотрудники, и ни на что не влияет. Метрики и пороги фиксируются до старта, стоп-критерий — первое ложное «подтверждено» ([пилот](PILOT.md)). Для юриста — карточка нормы на каждое правило ([пакет для юриста](legal/README.md)), для ИБ — карта норм и модель угроз, для ИТ — Docker и пилотный compose с `/readyz`. Что при допуске платежа проверяет «Мандат», а что остаётся за ДБО и банком, разведено заранее: нет ответа — нет допуска, поручение сверяет ДБО, идентификация и антифрод остаются процессами банка ([таблица ответственности](RUN.md#что-проверяет-мандат-и-что-остаётся-за-дбо-и-банком)). Интерес к пилоту подтвердили интервью. Граница: владельца процесса в ВТБ пока нет.

## Условия трека

| Условие | Как выполнено |
|---|---|
| Стек выбирает команда | Python 3.11–3.15, FastAPI, SQLite или Redis; без проприетарных зависимостей |
| Возможность соблюдать 152-ФЗ, 115-ФЗ и требования ИБ | раздел 1; [карта норм](DATA_PROTECTION_LAW.md) |
| Российский рынок и регулирование | МЧД по формату ФНС, ЕГРЮЛ, ЕФРСБ, ГК РФ, 63-ФЗ и 315-ФЗ; правила знают сроки норм ([ADR-010](adr/ADR-010-norm-validity.md)) |
| Интеграция с системами банка | порты к источникам, HTTP API по OpenAPI, контракт допуска для ДБО с таблицей ответственности «Мандат — ДБО — банк», вебхуки по Standard Webhooks |
| Open source | код под MIT, зависимости — открытые библиотеки с лицензиями в SBOM |
| Предпочтение российскому ПО | модель — российская по умолчанию ([ADR-005](adr/ADR-005-on-prem-models.md)); криптография ГОСТ — через СКЗИ банка; шрифт Golos Text — ParaType |
| On-prem в закрытом контуре | ядро работает без внешней сети (C-12), разворачивается из Docker в контуре банка |
| Генеративный ИИ на российских или on-prem моделях | клиент OpenAI-совместимого API для vLLM и llama.cpp в контуре (GigaChat Lightning, T-Pro), внешний хост — только если банк разрешит явно; модель выключена по умолчанию (`advisory/llm.py`) |
| Понимание масштабирования и надёжности | расчёт мощности в разделе 2; два узла, общий Redis, `/health` и `/readyz`, журнал с внешним якорем |
