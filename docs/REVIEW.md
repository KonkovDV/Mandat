# Разбор кейса человеком: роли и правила

Как устроен ручной разбор спорного кейса: роли, независимость второго мнения, хранение версий и маршруты HTTP API. Код: `src/mandat/review/state_machine.py`, `src/mandat/api/principals.py`, `src/mandat/api/review.py`; тесты: `tests/test_m09a_review_roles.py`, `tests/test_m09b_review_store.py`, `tests/test_m09c_review_api.py`.

## Роли

| Роль | Что может | Чего не может |
|---|---|---|
| `operator` | подать жалобу (`appeal`) от имени клиента; открыть кейс (`open`); закрыть кейс после решения (`close`) | решать: `accept`, `reject`, `request_docs` |
| `reviewer` | открыть кейс; решать: `accept`, `reject`, `request_docs`; закрыть кейс | подавать жалобу |
| `auditor` | только чтение | двигать кейс любым действием |
| `admin` | управлять пользователями и настройками | двигать кейс любым действием, в том числе решать |

Роли клиента нет: жалобу клиента подаёт `operator`, в журнале у записи `review_appeal` стоит `on_behalf_of: "client"`.

## Специализация reviewer

У `reviewer` есть атрибут `specialization`: `lawyer`, `compliance`, `security` или `client_service`.
В `MANDAT_API_USERS` он задаётся полем `specialization` и допустим только у `reviewer`.

Если у кейса задана `required_specialization`, решать его (`accept`, `reject`, `request_docs`) может только
`reviewer` с этой специализацией. Специализация решающего пишется в журнал (`details.specialization`).

Требование задаёт `operator` или `reviewer` действием `require` с полем `specialization` и основанием, пока кейс
в `queued`, `in_review` или `docs_requested` (журнал: `review_require`). Значение — одна из четырёх
специализаций; заданное требование не меняется (повтор того же значения допустим, другое — 409) и сохраняется
при `replace=true`.

Прежние имена ролей разбора (`lawyer`, `compliance`, `security`, `client_service`) принимаются как
`reviewer` с этой специализацией: так старые вызовы продолжают работать.

## Независимость решения

Решать кейс (`accept`, `reject`, `request_docs`) нельзя тому, кто:

- создал кейс (`created_by`);
- подал жалобу по нему (`appeal` в истории);
- принял решение, которое обжалуется (`appealed_decision_by`);
- после жалобы на решение человека — принимал любое решение по этому кейсу (`accept`, `reject`,
  `request_docs` в истории).

Открытие кейса (`open`) в счёт не идёт: открывший может его решать.

## Переходы

| Из | Действие | В | Роли |
|---|---|---|---|
| `auto_decided`, `accepted`, `rejected`, `closed` | `appeal` | `queued` | `operator` |
| `queued`, `in_review`, `docs_requested` | `require` | то же | `operator`, `reviewer` |
| `queued` | `open` | `in_review` | `operator`, `reviewer` |
| `docs_requested` | `open` | `in_review` | `operator`, `reviewer` |
| `in_review` | `request_docs` | `docs_requested` | `reviewer` |
| `in_review` | `accept` | `accepted` | `reviewer` |
| `in_review` | `reject` | `rejected` | `reviewer` |
| `accepted`, `rejected` | `close` | `closed` | `operator`, `reviewer` |

`close` — обычное действие со своими правилами и одно из действий маршрута `POST /v1/cases/{id}/review/{action}`,
а не отдельный маршрут.

## Хранение состояния

`Store.review_get(case_id)` возвращает состояние разбора и версию; `Store.review_put(case_id, state, expected_version)`
пишет, только если текущая версия равна ожидаемой (0 — разбора ещё нет), и возвращает новую версию. Иначе —
`ReviewVersionConflict` с ожидаемой и текущей версией; в API это ответ 409.

Сравнение и запись атомарны во всех хранилищах: в памяти — под блокировкой процесса, в SQLite — в одной транзакции
`BEGIN IMMEDIATE` (между процессами на одной машине), в Redis — одним Lua-скриптом (между машинами). Тест
`tests/test_m09b_review_store.py`: из N параллельных записей с одной версией проходит ровно одна, остальные получают
конфликт версии; для SQLite — и между процессами.

Хранилище не проверяет переходы и роли: это делает `ReviewCase` (выше). Состояние в памяти не переживает рестарт.

## API

Код: `src/mandat/api/app.py`, `src/mandat/api/review.py`; тесты: `tests/test_m09c_review_api.py`; контракт —
`docs/api/openapi.json`. Работает в режиме пользователей (`MANDAT_API_USERS`): у единственного токена стенда роль
`admin`, а она кейсы не двигает.

| Маршрут | Кто | Что |
|---|---|---|
| `GET /v1/cases/{id}/review` | владелец кейса, любой `reviewer`, `auditor`, `admin` | состояние, `version`, приоритет, срок, история |
| `POST /v1/cases/{id}/review/{action}` | по таблице переходов; оператор — только по своим кейсам | `appeal`, `require`, `open`, `accept`, `reject`, `request_docs`, `close` |
| `GET /v1/review/queue` | `reviewer`, `auditor`, `admin` — все; `operator` — свои | кейсы в `queued`, `in_review`, `docs_requested`: сначала просроченные, затем по поднятому приоритету и сроку |

Тело действия: `{"expected_version": <version из GET>, "reason": "..."}`, у `require` ещё `"specialization"`
(в других действиях это поле — 422). Ответы: 200 — новое состояние и версия;
403 — роль, специализация или независимость решения; 404 — кейса нет или он не виден; 409 — версия устарела
(в том числе `ReviewVersionConflict` при записи) или переход недопустим из текущего состояния; 422 — нет основания
или версии; 503 — журнал не настроен в pilot/prod, журнал не цел или хранилище недоступно. Чужой кейс оператору
неотличим от несуществующего (404).

Разбор создаётся вместе с кейсом (версия 1): подтверждённый вердикт — `auto_decided`, остальные — `queued` с
приоритетом из отчёта. Жалоба (`appeal`) на автоматическое решение ставит кейс в очередь с приоритетом P2: у такого
отчёта своего приоритета нет. Жалоба на решение человека (`accept`, `reject`, в том числе после `close`) тоже
возвращает кейс в очередь; решивший его раньше по этому кейсу не решает (см. «Независимость решения»).
При `replace=true` с другим отчётом разбор начинается заново: прежний (состояние и история) уходит в
`superseded`, в журнал пишется `review_reset`, версия продолжает расти. Тот же отчёт разбор не трогает.
Номер кейса при списке пользователей выдаёт сервер, поэтому перезапись возможна только в режиме одного токена.
Решение пишется в журнал до записи в хранилище; запись журнала с той же версией от
другого сотрудника даёт 409. В pilot и prod без журнала (`MANDAT_API_JOURNAL`) действие не принимается (503).

## SLA

Значения по умолчанию — P1 4 ч, P2 24 ч, P3 72 ч (`src/mandat/services/next_steps.py`). Они не взяты ни из какой
нормы; реальные сроки задаёт банк в `MANDAT_REVIEW_SLA_HOURS`, JSON вида `{"P1": 2, "P2": 8}`: не заданные
приоритеты берут значения по умолчанию. Значение проверяется при старте API: неверное — API не стартует, а не
откатывается молча и не отвечает 500 на запросах. Срок (`due_at`) — время
постановки в очередь плюс SLA приоритета; считается при каждом запросе, так что новые значения действуют и для
кейсов, уже стоящих в очереди.

Эскалация: после `due_at` кейс помечается `overdue`, `escalation_level` — 1 плюс число полных периодов SLA
просрочки, `effective_priority` поднимается на столько же ступеней (P3 → P2 → P1, выше P1 нет). Это поля
`GET /v1/cases/{id}/review` и очереди; считаются при чтении, хранимый `priority` не меняется.

## Ограничения

- Эскалация только в ответах API: уведомлений, фоновой задачи и записи в журнал при просрочке нет.
- Если запись разбора при создании кейса не удалась, кейс не виден в очереди до первого действия (разбор с версии 0);
  сбой пишется в журнал сервера (`review_seed_failed` с `case_id`).
- Кейс, отчёт которого вытеснен из хранилища (`MAX_REPORTS`), из очереди пропадает.
