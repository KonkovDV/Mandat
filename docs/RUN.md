# Запуск, команды и API

Как запустить стенд, проверить удостоверения и журнал, поднять API и какие переменные окружения он читает. Коротко про демо — в [README](../README.md#запустить-демо). Нужен Python 3.11 или новее; CI проверяет 3.11–3.15, образ Docker собран на 3.15.

Linux, macOS или WSL, без установки в систему:

```bash
./run-demo.sh
```

На Windows — `.\run-demo.ps1` или WSL: реестр статусов блокируется `msvcrt.locking` вместо `flock`, базу часовых поясов даёт пакет `tzdata`. Полный `pytest` на Windows идёт в CI, задача `windows`.

Из установленного пакета:

```bash
pip install -e ".[dev,api]"
mandat demo
mandat verify examples/cases/10_old_director_poa --html var/10.html
mandat attest-verify var/demo/attestations/01_ok.json --public-key-file var/demo/public_key.txt --status-dir var/demo/status
mandat monitor examples/events/poa_revoked.json --status-dir var/demo/status
mandat monitor examples/events/takeover.json --status-dir var/demo/status
mandat monitor examples/events/poa_expiring.json   # сроки МЧД: за 30 дней — предупреждение, после срока — отзыв
mandat attest-verify var/demo/attestations/01_ok.json --public-key-file var/demo/public_key.txt --status-dir var/demo/status
mandat journal-proof var/demo/journal.jsonl --seq 3
python -m pytest
```

Порядок важен для демонстрации статусов. Первый `attest-verify` идёт до событий и выходит с кодом 0: удостоверение действует. Событие захвата из `takeover.json` приостанавливает удостоверения организации, поэтому второй `attest-verify` печатает «приостановлено» и выходит с кодом 3. Это ожидаемый результат, а не сбой: код 3 значит «подпись верна, но статус не "действует"». Команда печатает и вердикт из удостоверения: удостоверение опровергнутого кейса тоже действительно, решение по операции принимается по вердикту. Код 2 — ошибка вызова/конфигурации (нет ключа издателя, в `pilot`/`prod` нет `--status-dir` без `--crypto-only`, битые аргументы). Код 4 — подпись верна, но удостоверение не принимается: истёк срок, чужой издатель или назначение, профиль demo в защищённом режиме. Чтобы вернуться к исходному состоянию, снова выполните `mandat demo`.

Для проверок как в CI зависимости ставятся из lock-файлов с хешами ([CONTRIBUTING](../CONTRIBUTING.md#проверки-перед-pr)). Проверка на Cedar ставится отдельно: `pip install -e ".[dev,api,cedar]"`.

Готовый образ из релиза, с подписью и аттестацией происхождения ([как проверить](../SECURITY.md#проверить-пакет)):

```bash
docker pull ghcr.io/konkovdv/mandat:0.4.0
```

## API

Docker поднимает API только на localhost: `docker compose up --build`. Сначала положите в `.env` токен или список пользователей (образец в `.env.example`). Без них compose не стартует, чтобы стенд не оказался открыт с паролем по умолчанию.

Режимов доступа два. Нужен хотя бы один: без обоих `mandat serve` и контейнер из `docker-compose.yml` не стартуют и пишут, что задать.

| Режим | Как включить | Что получается |
|---|---|---|
| Стенд | `MANDAT_API_TOKEN` | один токен с правами администратора, `case_id` задаёт клиент, повтор даёт 409, перезапись через `?replace=true`. Если задан и `MANDAT_API_USERS`, этот токен не действует |
| Пользователи | `MANDAT_API_USERS`: JSON-массив или путь к файлу | у каждого имя, роль и SHA-256 токена; два пользователя с одним токеном не допускаются. `case_id` выдаёт сервер, клиентский сохраняется как `client_case_id` |

| Роль | Создаёт кейсы и события | Видит кейсы | Действия разбора |
|---|---|---|---|
| `operator` | да | только свои | `appeal`, `open`, `close`, `require` |
| `reviewer` | да | только свои, в разборе — любые | `open`, `request_docs`, `accept`, `reject`, `close`, `require` |
| `auditor` | нет | все | нет |
| `admin` | да | все | нет |
| `dbo` | нет | нет | нет |

`dbo` — служебная учётная запись системы банка, которая проводит операцию: она только запрашивает допуск операции для своих получателей удостоверений (`audiences`), кейсы не создаёт и отчёты с ПДн не читает. В `pilot` и `prod` допуск выдаётся только ей, а `audiences` обязательны.

Чужой кейс отвечает 404, как несуществующий. Токен и строку для списка выпускает `mandat api-user --name ivanova --role operator`, для системы банка — `mandat api-user --name dbo-msb --role dbo --audience bank-dbo-msb --expires-in-days 90`; сам токен показывается один раз.

### Маршруты

Контракт — [`docs/api/openapi.json`](api/openapi.json), Swagger на `/docs` включается `MANDAT_API_DOCS=1`.

| Маршрут | Кто вызывает | Что делает |
|---|---|---|
| `GET /health` | без токена | процесс жив: движок, настроен ли доступ, режим, хранилище |
| `GET /readyz` | без токена | готовность: журнал, хранилище, ключи; 200 или 503, в теле только имена проверок |
| `POST /v1/cases` | `operator`, `reviewer`, `admin` | проверка кейса по манифесту JSON; `?profile=`, `?replace=true`, заголовок `Idempotency-Key`: повтор отдаёт прежний отчёт только владельцу и пишется в журнал как чтение (`read_case`) |
| `GET /v1/cases/{id}` | владелец кейса, `auditor`, `admin` | отчёт JSON; каждое чтение пишется в журнал (`read_case`) |
| `GET /v1/cases/{id}/report.html` | то же | карточка сотрудника |
| `POST /v1/cases/{id}/erase` | `admin` | удаление отчёта с ПДн по основанию из 152-ФЗ: тело `{"reason": "unlawful_processing" \| "purpose_achieved" \| "consent_withdrawn" \| "subject_request"}`; запись в журнал без данных ([защита данных](DATA_PROTECTION.md#удаление-кейса)) |
| `GET /v1/cases/{id}/review` | то же и `reviewer` | состояние разбора и версия для `expected_version` |
| `POST /v1/cases/{id}/review/{action}` | `operator`, `reviewer` | действие разбора: `appeal`, `open`, `accept`, `reject`, `request_docs`, `close`, `require` ([разбор](REVIEW.md)) |
| `GET /v1/review/queue` | любая роль; `operator` видит свои кейсы | кейсы, ждущие человека, по сроку |
| `POST /v1/events` | `operator`, `reviewer`, `admin` | оценка событий мониторинга и сроков МЧД: момент — `as_of` в теле или время сервера, `notice_days` — за сколько дней предупреждать (по умолчанию 30); повтор того же события тревоги не дублирует, ответ — до 1 000 000 связей «тревога — право», больше — 422; статусы удостоверений не меняет, их пишет `mandat monitor` |
| `POST /v1/operations/authorize` | `dbo` для своих `audiences`; на стенде также `operator`, `reviewer`, `admin` | допуск одной операции по удостоверению ([ниже](#допуск-операции-для-дбо)) |
| `GET /.well-known/authzen-configuration` | любая роль | метаданные точки решений по OpenID AuthZEN 1.0 ([ниже](#допуск-по-openid-authzen-10)) |
| `POST /access/v1/evaluation` | как у `/v1/operations/authorize` | тот же допуск в конверте AuthZEN: одна оценка |
| `POST /access/v1/evaluations` | то же | пакет оценок: `execute_all`, `deny_on_first_deny`, `permit_on_first_permit` |

Любой ответ API несёт `X-Request-ID`. Если вызывающая система прислала свой идентификатор из безопасного алфавита (буквы, цифры, `.`, `_`, `~`, `:`, `+`, `/`, `=`, `-`, до 128 знаков), он возвращается тем же, иначе сервер выдаёт свой. В журнал сервера присланный идентификатор попадает через ту же маску номеров, что и путь. На `401` приходит `WWW-Authenticate: Bearer` (RFC 6750): без токена — только схема, с неверным — `error="invalid_token"`.

Манифест сверяется с [контрактом](api/case-manifest.schema.json). В `pilot`, `prod` и любом защищённом режиме поле вне контракта — 422: опечатка в имени поля не превращается в «источник недоступен». На стенде такой кейс проверяется, а отчёт называет непрочитанное поле в предупреждениях.

### Допуск операции для ДБО

Банк проверяет полномочие в два шага, как разделяет VC Data Model 2.0 проверку подлинности и решение проверяющего:

1. `POST /v1/cases` — проверка кейса; по отчёту «Мандат» выпускает удостоверение со статусом, привязанное к организации, дню операции, операции, сумме, токену представителя, получателю (`audience`) и одноразовому `nonce`.
2. Перед операцией ДБО присылает удостоверение и запрос операции на `POST /v1/operations/authorize`:

```json
{
  "credential": {"...": "удостоверение «Мандата»"},
  "request": {
    "organization_inn": "7707083893",
    "operation": "PAYMENT_SIGN",
    "operation_date": "2026-11-17",
    "amount_rub": 500000,
    "representative_inn": "123456789012",
    "audience": "bank-dbo-msb",
    "nonce": "n-0123456789abcdef"
  },
  "operation_risk": "payment"
}
```

Ответ `200`: `{"allowed": true, "problems": [], "already_admitted": false, "admitted_at": null, …}` или `{"allowed": false, "problems": ["…"], …}`. Отказ — тоже ответ, а не ошибка: причины перечислены. Решение принимает `authorize_operation` без ослаблений: подпись и срок удостоверения, статус по спискам, вердикт `confirmed`, организация, день операции по Москве по часам сервера, операция, сумма не больше проверенной, представитель (по HMAC-токену, ИНН в журнал не пишется), получатель и `nonce`.

- `nonce` расходуется атомарно в общем хранилище (`claim` в памяти, SQLite и Redis) и только при допуске: чужой запрос его не «сжигает». Из одновременных повторов допуск получает один.
- Потерянный ответ. Вместе с `nonce` хранится отпечаток удостоверения и запроса (HMAC на ключе представителя) и время допуска. Если ДБО не получил ответ и прислал тот же запрос снова, ответ — отказ с `"already_admitted": true` и `admitted_at` — временем первого допуска: операцию по первому допуску ДБО проводит один раз, второго допуска нет. Тот же `nonce` с другим запросом — отказ «nonce уже использован другим запросом» без признака. Если удостоверение после допуска отозвано или приостановлено, повтор получает отказ по статусу, а не признак.
- High-watermark списков статусов лежит в том же хранилище и только растёт: подложенный старый список — отказ.
- Каждое решение пишется в журнал (`authorize_operation`): допуск, операция, получатель, число причин отказа. Если журнал недоступен, допуск не выдаётся (`503`), а `nonce`, который занял этот запрос, освобождается: повтор того же запроса проверяется заново. Если недоступно и хранилище, повтор получит отказ.
- `503` — допуск не настроен или в `pilot` и `prod` нет общего хранилища и журнала. `422` — запрос не по схеме (лишнее поле, сумма не целым числом, дата не `ГГГГ-ММ-ДД`).
- `403` — допуск запросил не тот: в `pilot` и `prod` сотрудник, а не учётная запись `dbo`, либо `audience` запроса не из `audiences` этой учётной записи. `nonce` при таком отказе не расходуется.

Ответ — допуск по удостоверению «Мандата», а не разрешение операции целиком: идентификация клиента, антифрод и договор ДБО остаются процессами банка ([ступени готовности](READINESS.md)).

### Что проверяет «Мандат» и что остаётся за ДБО и банком

Разделение ответственности при допуске платежа. Так устроены открытые разборы протокола AP2: отдельно перечислено, что проверяет библиотека, а что интегратор обязан проверить сам ([открытые репозитории](COMPETITORS.md#открытые-репозитории-что-нашли-и-что-учли)). Юристу банка и интегратору ДБО это нужно до договора, а не после инцидента.

| Что проверяется | Кто | Как |
|---|---|---|
| полномочие представителя на дату операции: МЧД, ЕГРЮЛ, устав, передоверие, банкротство | «Мандат» | `POST /v1/cases`, 39 правил с нормой |
| подлинность и статус удостоверения | «Мандат» | подпись eddsa-jcs-2022, списки статусов W3C, high-watermark |
| запрос совпадает с удостоверением: организация, день, операция, сумма не выше, представитель, получатель | «Мандат» | `authorize_operation` |
| одноразовость: один допуск на `nonce`, повтор после потерянного ответа узнаёт первый допуск | «Мандат» | общее хранилище |
| след решения | «Мандат» | запись `authorize_operation` в журнале; без журнала допуска нет |
| запрос допуска описывает именно это платёжное поручение: сумма и получатель в поручении те же | ДБО | «Мандат» видит запрос, а не поручение |
| свежий `nonce` на каждую операцию, допуск не кэшируется и не переиспользуется | ДБО | — |
| нет ответа — нет допуска: `503`, таймаут и обрыв связи считаются отказом; другой режим на время недоступности «Мандата» — решение банка | ДБО и банк | — |
| вход клиента в ДБО и подпись поручения, проверка сертификата КЭП | ДБО и СКЗИ банка | 63-ФЗ; ГОСТ-криптография — через СКЗИ банка |
| идентификация клиента и представителя, признаки операций без согласия клиента | банк | 115-ФЗ, ст. 7; 161-ФЗ, ст. 8 и признаки Банка России |
| порядок отмены полномочий в договоре ДБО и уведомление банка об отмене | банк и клиент | ст. 189 ГК РФ: банк, который не знал и не должен был знать об отмене, защищён, поэтому реестр МЧД сверяется на дату операции |

### Допуск по OpenID AuthZEN 1.0

AuthZEN Authorization API 1.0 — финальная спецификация OpenID Foundation от 12.01.2026: общий язык между точкой применения решения (PEP: ДБО, шлюз API, антифрод) и точкой принятия решения (PDP). «Мандат» отвечает по нему как PDP, и шлюз, который уже говорит на AuthZEN, подключается без своего адаптера. Решение считает та же функция, что и `/v1/operations/authorize`: меняется конверт, а не правила.

```json
{
  "subject": {"type": "representative", "id": "123456789012"},
  "resource": {"type": "organization", "id": "7707083893"},
  "action": {"name": "PAYMENT_SIGN", "properties": {"operation_date": "2026-11-17", "amount_rub": 500000}},
  "context": {
    "credential": {"...": "удостоверение «Мандата»"},
    "nonce": "n-0123456789abcdef",
    "audience": "bank-dbo-msb",
    "operation_risk": "payment"
  }
}
```

Ответ `200`: `{"decision": true, "context": {"checked_at": "…"}}` или `{"decision": false, "context": {"problems": ["…"], "reason_admin": {"403": "…"}, "reason_user": {"403": "Операция не допущена: обратитесь в банк"}}}`; повтор допущенного запроса — `decision: false` с `already_admitted` и `admitted_at`.

- Поля вне профиля игнорируются (раздел 10.1.1 спецификации). Без обязательного поля, с неверным типом `subject` или `resource`, с коротким `nonce` или датой не `ГГГГ-ММ-ДД` — `400`, и `nonce` не расходуется. Тело читается как I-JSON: повтор ключа и `NaN` — тоже `400`.
- Пакет (раздел 7): верхние `subject`, `action`, `resource`, `context` — значения по умолчанию, ключ оценки заменяет верхний целиком. Ошибка одной оценки — её `decision: false` с `context.error`; ошибка структуры пакета — `400` до первой оценки. `deny_on_first_deny` и `permit_on_first_permit` останавливаются на первом отказе или допуске, остальные оценки не выполняются и `nonce` не тратят. Не больше 64 оценок в пакете.
- Метаданные (раздел 9): `policy_decision_point` берётся из `MANDAT_AUTHZEN_PDP` (адрес `https` без запроса и фрагмента). На стенде без неё — адрес запроса, в `pilot` и `prod` — `503`. В метаданных только реализованные адреса: поиска субъектов, ресурсов и действий (раздел 8) нет, PDP без состояния не знает, кто ещё вправе действовать за организацию.
- Каждая оценка пишется в журнал как `authorize_operation` с `via: authzen`. Ответ не подписывается: раздел 11.6 это допускает, подлинность держат TLS и журнал.

### Эксплуатация: ревизия доступа, восстановление, инцидент

Команды из чек-листа перед пилотом ([PILOT_CHECKLIST](PILOT_CHECKLIST.md)):

```bash
mandat api-user --name contractor --role operator --expires-in-days 14 --owner "Петров, ИБ"
mandat access-review --strict
```

`--owner` — кто отзовёт доступ, когда работа закончится. Ревизия печатает учётные записи без срока, с долгим сроком (дольше 90 дней), с концом срока в ближайшие 14 дней и без владельца отзыва; с `--strict` — код 1, если у действующей записи нет срока или владельца. Токены и хеши в ответ не попадают.

```bash
mandat restore-check --journal var/api/journal.jsonl --store sqlite:///var/api/store.db --status-dir var/status --repair
```

После восстановления хранилища и списков статусов из копии. Журнал ведётся дальше и служит опорой: удалённый после снятия копии кейс снова удаляется вместе с историей разбора, отзыв или приостановка из журнала снова выставляются в списке (нужен ключ подписи списков), нечитаемая запись — нарушение. Починка пишется в журнал (`erase_case` с `reapplied_after_restore`). Без `--repair` команда только сверяет; с повреждённым журналом не чинит ничего. Код 0 — всё сверено.

```bash
mandat incident-report --journal var/api/journal.jsonl --detected-at 2026-11-20T09:00:00+03:00
```

Сроки по ч. 3.1 ст. 21 152-ФЗ — оба от выявления: уведомление за 24 часа, результаты расследования за 72 часа (не 24 + 72). Из журнала — кто, сколько раз и сколько кейсов создавал, читал и удалял до выявления; `--since`, `--until` и `--actor` сужают окно. Если журнал не прошёл проверку, фактов из него нет.

Окно лимита частоты и отчёты лежат в хранилище `MANDAT_API_STORE`:

| Значение | Когда | Что нужно |
|---|---|---|
| пусто или `memory` | один процесс, стенд | ничего |
| `sqlite:///var/api.db` | несколько воркеров на одной машине: `mandat serve --workers 4` | только стандартная библиотека, файл в режиме WAL |
| `redis://хост:6379/0` | несколько машин за балансировщиком | `pip install "mandat[redis]"` |

С `--workers` больше одного и хранилищем в памяти `mandat serve` не стартует: у каждого воркера был бы свой лимит и свои отчёты.

## Календарь норм

```bash
mandat law-calendar --on 2027-08-01 --days 240
```

Показывает акты из каталога пакета правил: состояние на дату, что вступает в силу и что утрачивает её в окне, на какие правила это влияет. Код 1 — на дату есть акт, утративший силу, а правила на нём не пересверены: команду удобно ставить в планировщик ([ADR-010](adr/ADR-010-norm-validity.md), [календарь изменений](REGULATORY.md#календарь-изменений)).

## Сайт проекта

```bash
python scripts/build_site.py --out _site
```

Страница — шаблон `site/index.html`: числа подставляются из `evidence.json`, календарь норм — из пакета правил, 14 отчётов демо собирает `mandat demo`. На сайт уходят только HTML-отчёты: ключи стенда, журнал и удостоверения демо остаются во временном каталоге. Шрифт Golos (WOFF2, кириллица и латиница), стили и иконки лежат рядом: внешних запросов и скриптов у страницы нет. Схема цепочки полномочий в первом экране и появление разделов при прокрутке сделаны на CSS и выключаются, если в системе включено «уменьшить движение». Тема светлая или тёмная — по настройке устройства.

Вёрстка проверяется на матрице устройств — от сложенного Galaxy Z Fold (280 px) до монитора 2560 px, в светлой и тёмной теме, с каждым из 14 отчётов демо:

```bash
(cd scripts && npm ci)
node scripts/check_site_devices.js _site
```

Скрипт отдаёт сайт по HTTP, как GitHub Pages, и ищет горизонтальную прокрутку, неудачные запросы, ошибки в консоли, незагруженный шрифт, битые якоря, картинки без `alt` и цели касания ниже 40 px. Playwright и axe-core ставит `npm ci` из `scripts/package-lock.json`, axe-core проверяет каждую страницу на WCAG 2.2 AA; в CI то же делает задача `devices` в `pages.yml`. Safari и Firefox этим скриптом не проверяются.

Задача CI `pages` собирает сайт на каждом PR и push в `main`. Публикация включается владельцем один раз: Settings → Pages → Source: GitHub Actions, затем Settings → Secrets and variables → Actions → Variables → `PAGES_ENABLED` = `true`. До этого публикация пропускается, а проверки остаются зелёными.
