# ADR-003. Правила — данные с нормой и статусом, логика — код с тестом

**Контекст.** Банку нужно менять формулировки норм, коды полномочий и теги формата без релиза, а юристу — утверждать каждое правило. Писать произвольную логику на JSON-языке правил сложно проверять.

**Решение.**
- `data/rules.json`: идентификатор, группа, норма, допустимые эффекты, статус (`draft`, `approved`, `retired`), параметры банка (`params`, например окно свежести смены руководителя), следующий шаг, подразделение, ссылки на тесты. Хеш пакета попадает в каждый отчёт и удостоверение. Параметры — настройки банка, а не нормы.
- `data/operations.json`: операции банка и коды полномочий, которые их покрывают.
- `data/emchd_003_mapping.json`: пути к полям формата МЧД и значения признаков.
- `data/authority_classifier.json`: снимок классификатора полномочий с датами (ADR-008).
- Логика правила — функция в `rules/checks.py`. Тест сверяет, что у каждого правила пакета есть реализация, а у каждого правила — существующий тест.
- В профиле `strict` опровержение по правилу без статуса `approved` понижается до разбора, а проверка подписи обязательна. Пока СКЗИ не подключены, итог почти везде — «недостаточно данных» (`docs/EVALUATION.md`).

**Альтернативы.** OPA/Rego или Datalog дают декларативность, но добавляют среду исполнения и язык, который банку придётся сопровождать. Можно перейти, когда правил станет больше сотни: метаданные пакета уже отделены.
