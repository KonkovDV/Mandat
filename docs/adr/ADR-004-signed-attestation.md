# ADR-004. Результат проверки — подписанное удостоверение

Решение: на каждый отчёт выпускается подписанное удостоверение в модели W3C VC 2.0. ДБО, антифрод или аудит проверяют его без доступа к базе «Мандата».

**Контекст.** Результат проверки нужен другим системам банка. Ориентир — роли сотрудников как проверяемые удостоверения в GLEIF vLEI.

**Решение.**
- Доказательство Data Integrity по образцу `eddsa-jcs-2022`: хеш конфигурации доказательства и хеш документа, подпись Ed25519, значение в base58btc. Каноническая запись — RFC 8785 (`audit/jcs.py`), проверена на примерах из RFC.
- Внутри: ИНН организации, токен представителя, операция, вердикт, профиль, хеши набора правил, отчёта и входных документов. ФИО и паспорта нет.
- Токен представителя — HMAC-SHA256 на ключе издателя. Простой хеш 12-значного ИНН подбирается перебором.
- «Подпись верна» ещё не значит «принимается». `validate_attestation` проверяет доверенный ключ, издателя, назначение, криптонабор, срок `validUntil`, профиль (demo в защищённом режиме не принимается) и статус.

**Проверка.** `test_attestation_sign_verify_and_tamper`, `tests/test_attestation_validation.py`, `tests/test_jcs.py`, команда `mandat attest-verify`.

**Ограничения.** С внешними верификаторами VC совместимость не проверялась. Издатель — `did:web:mandat.example`, в пилоте нужны ключ и идентификатор банка. Подпись Ed25519, не ГОСТ. Идея взята из fsp-talent ([PORTING](../PORTING.md)).
