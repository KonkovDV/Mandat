# Модель ключей

Какие ключи нужны Мандату, как их создавать, где хранить, как менять и как после смены проверять старые журналы и удостоверения. Для демо ключи создаются сами в `var/demo/keys/`; в пилоте и проде так делать нельзя.

## Перечень

| Ключ | Где задаётся | Назначение | Требование при `MANDAT_ENV=pilot/prod` |
|---|---|---|---|
| HMAC журнала | `MANDAT_JOURNAL_KEY` | подпись записей и файла-свидетеля журнала решений | обязателен, не короче 32 байт |
| Псевдонимизация ПДн | `MANDAT_PII_KEY` | HMAC-токены ИНН/СНИЛС в логах и запросах к модели | обязателен, не короче 32 байт |
| Токен стенда | `MANDAT_API_TOKEN` | общий токен роли `admin`, только без `MANDAT_API_USERS` | не короче 32 байт; в пилоте лучше `MANDAT_API_USERS` |
| Токены пользователей | `MANDAT_API_USERS` | хеши SHA-256 токенов с ролями | токены выдаёт `mandat api-user` |
| Подпись удостоверений | `MANDAT_SIGNER`: `file` (PEM), `pkcs11`, `vault`, `aws-kms` | подпись удостоверений и списка статусов | открытый PEM запрещён: PEM, зашифрованный фразой `MANDAT_SIGNING_KEY_PASSPHRASE` (от 16 байт), или HSM/KMS |
| HMAC представителя | `keys/representative_hmac.key` | токен представителя в удостоверении | не короче 32 байт |
| Секрет вебхуков | `MANDAT_WEBHOOK_SECRET` | Standard Webhooks, `whsec_` 24–64 байт | обязателен формат `whsec_` |

С 14.10.2026 `mandat serve` проверяет ключ журнала, ключ ПДн и длину токена стенда при старте и в защищённом режиме не запускается без них (код выхода 2). Раньше нехватка ключа обнаруживалась только на первой записи.

## Создание

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"   # MANDAT_JOURNAL_KEY, MANDAT_PII_KEY, MANDAT_API_TOKEN
mandat webhook-secret                                          # MANDAT_WEBHOOK_SECRET
mandat api-user <имя> <роль>                                   # строка для MANDAT_API_USERS
```

Ключ создаётся на машине, где он будет храниться, и не проходит через почту, чаты, тикеты и git. `.env` в репозиторий не кладётся.

## Хранение

1. **Пилот и прод: KMS или HSM банка.** Секреты HMAC выдаются процессу как переменные окружения из хранилища секретов (Vault, KMS-оператор Kubernetes, systemd `LoadCredential`). Ключ Ed25519 для удостоверений живёт в HSM или KMS и не покидает модуль: Мандат получает только подпись (раздел «Подписант удостоверений» ниже).
2. **Стенд: переменные окружения или файл 0600** под непривилегированным пользователем, каталог `var/` не публикуется.
3. Ключи разных контуров (стенд, пилот, прод) не совпадают.

## Ротация

Плановая смена — не реже раза в год и сразу при подозрении на утечку или уходе сотрудника с доступом.

| Ключ | Порядок | Проверка старого |
|---|---|---|
| `MANDAT_JOURNAL_KEY` | закрыть текущий журнал, сохранить его хеш как внешний якорь (SECURITY.md), начать новый файл журнала с новым ключом | старый ключ переводится в архив только для чтения; `mandat journal-verify` старого файла запускается со старым ключом |
| `MANDAT_PII_KEY` | заменить ключ; токены до и после смены не сопоставляются — это ожидаемо | старые токены сверяются только старым ключом из архива |
| Ed25519 удостоверений | выпустить новую пару, опубликовать новый открытый ключ рядом со старым, переключить выпуск | проверка принимает список доверенных ключей (`validate_attestation(cred, [новый, старый])`); старый ключ убирается из списка, когда истёк срок принятия всех выданных им удостоверений (30 дней) |
| `MANDAT_WEBHOOK_SECRET` | новый и старый через пробел, новый первым; через окно доставки убрать старый | получатель принимает любую из подписей |
| Токены API | выдать новый через `mandat api-user`, удалить старую запись из `MANDAT_API_USERS`, перезапустить | — |

При компрометации ключа подписи удостоверений все выданные им удостоверения отзываются через список статусов, а старый открытый ключ сразу удаляется из доверенных.

## Подписант удостоверений (RT-05)

Код: `src/mandat/audit/signing.py`. Подписант (`Signer`) отдаёт идентификатор ключа, открытый ключ и подпись; закрытый ключ из HSM/KMS не извлекается. Каждая подпись перед выпуском проверяется открытым ключом подписанта: если модуль подписал другой версией ключа, удостоверение не выпускается.

| `MANDAT_SIGNER` | Где ключ | Настройки | Зависимость |
|---|---|---|---|
| `file` (по умолчанию) | PEM PKCS#8 на диске, права 0600 | `MANDAT_SIGNING_KEY_FILE`, `MANDAT_SIGNING_KEY_PASSPHRASE` (шифрование PBES2/AES-256). Без фразы — только demo/dev/test | нет |
| `pkcs11` | HSM, токен, SoftHSM; механизм `CKM_EDDSA` (PKCS#11 v3.0) | `MANDAT_PKCS11_LIB`, `MANDAT_PKCS11_TOKEN`, `MANDAT_PKCS11_KEY_LABEL`, `MANDAT_PKCS11_PIN` | extra `[pkcs11]` (python-pkcs11) |
| `vault` | HashiCorp Vault Transit, ключ типа `ed25519` | `VAULT_ADDR` (https), `VAULT_TOKEN`, `MANDAT_VAULT_KEY`, `MANDAT_VAULT_MOUNT`, `MANDAT_VAULT_KEY_VERSION` (по умолчанию последняя, закрепляется при старте) | нет (stdlib) |
| `aws-kms` | AWS KMS, `ECC_NIST_EDWARDS25519`, `ED25519_SHA_512` с `MessageType=RAW` | `MANDAT_KMS_KEY_ID`, учётные данные AWS стандартной цепочкой | extra `[aws]` (boto3) |

GCP Cloud KMS (`EC_SIGN_ED25519`) подключается так же, как AWS: по тому же интерфейсу из трёх методов; адаптер не входит в поставку. Yandex Cloud KMS Ed25519 не поддерживает (только RSA-PSS и ECDSA), поэтому для него нужна смена криптонабора удостоверений — не сделано.

### Идентификатор ключа и связка

Идентификатор ключа — multibase открытого ключа (`z6Mk…`, как в did:key). Он стоит в подписанной части доказательства: `proof.verificationMethod = did:web:mandat.example#<kid>`, поэтому подменить его, не сломав подпись, нельзя. Проверяющий берёт ключ из связки по kid — как `kid` в JWKS (RFC 7517).

Связка ключей (`mandat attest-verify … --keyring keyring.json`):

```json
{"keys": [
  {"kid": "z6Mk…новый", "status": "active"},
  {"kid": "z6Mk…старый", "status": "retired", "retired_at": "2026-10-14T00:00:00+03:00"},
  {"kid": "z6Mk…утёкший", "status": "revoked"}
]}
```

- `active` — текущий ключ выпуска; им же переподписываются списки статусов.
- `retired` — выведен из выпуска; проверяет только удостоверения с `proof.created` не позже `retired_at`. Подпись старым ключом после вывода не принимается.
- `revoked` — скомпрометирован; не проверяет ничего, выданные им удостоверения отзываются.

Список статусов после ротации переподписывается новым ключом, а удостоверение остаётся подписанным старым: проверка статуса ищет ключ списка по его собственному kid среди `active`.

### Ротация ключа подписи

1. Создать новый ключ в HSM/KMS (или новую версию в Vault: `vault write -f transit/keys/mandat/rotate`).
2. Добавить его kid в связку со статусом `active`, старый перевести в `retired` с текущим временем; опубликовать связку проверяющим.
3. Переключить выпуск (`MANDAT_VAULT_KEY_VERSION`, метку PKCS#11 или ключ KMS) и перезапустить; выполнить `mandat monitor`, чтобы списки статусов переподписались.
4. Через срок принятия удостоверений (30 дней, `VALID_FOR`) удалить старый ключ из связки и уничтожить его в модуле.

NIST SP 800-57 рекомендует криптопериод закрытого ключа подписи 1–3 года; для удостоверений со сроком 30 дней разумно 1 год.

### Российский контекст

Ed25519 в Мандате подписывает внутренние удостоверения о проверке полномочий; это не электронная подпись по 63-ФЗ и не замена КЭП. Если удостоверение будет использоваться в контуре переводов денежных средств или станет юридически значимым, требования 821-П и ФСБ означают переход на ГОСТ Р 34.10-2012 / 34.11-2012 в сертифицированном СКЗИ (например, через PKCS#11-интерфейс сертифицированного HSM). Интерфейс `Signer` для этого готов, но криптонабор `eddsa-jcs-2022` придётся заменить своим (ГОСТ в W3C Data Integrity не стандартизован) — это решение банка и юриста, не сделано. Требования ФСТЭК к защите информации (приказы № 17, 21, 239 по классу системы) касаются инфраструктуры стенда и описываются в модели угроз банка.

## Что открыто

- Адаптер GCP Cloud KMS и проверка на реальном HSM/SoftHSM (сейчас адаптеры проверены на заглушках интерфейсов; SoftHSM в CI не ставится).
- Криптонабор ГОСТ для юридически значимого контура.
- Автоматическая ротация ключа журнала с цепочкой «последняя запись старого журнала → первая нового».
- Решение банка о сроке хранения архивных ключей.

## Внешний якорь журнала

Хеш каждого закрытого сегмента журнала (1000 записей, `MANDAT_JOURNAL_SEGMENT_RECORDS`) публикуется вне машины (`src/mandat/audit/anchor.py`). Без якоря root на хосте с ключом журнала может переписать сегменты и свидетель так, что цепочка и HMAC сойдутся.

| Переменная | Значение |
|---|---|
| `MANDAT_JOURNAL_ANCHOR` | приёмники через запятую: `file:/путь/на/другом/томе`, `webhook:https://…`, `tsa:https://…` (RFC 3161, `pip install 'mandat[tsa]'`), `rekor:https://rekor.sigstore.dev` |
| `MANDAT_JOURNAL_ANCHOR_SECRET` | секрет Standard Webhooks для `webhook:` (`mandat webhook-secret`) |
| `MANDAT_JOURNAL_ANCHOR_TSA_ROOTS` | PEM-файл доверенных корней TSA: цепочка сертификата TSA проверяется на момент метки, EKU — только timeStamping (critical) |
| `MANDAT_JOURNAL_ANCHOR_TSA_CERT` | SHA-256 DER-сертификата TSA: метка с другим сертификатом не принимается. Нужен хотя бы один из двух параметров TSA |
| `MANDAT_JOURNAL_ANCHOR_REKOR_KEY` | путь к ключу ECDSA P-256 (PEM) для записей hashedrekord |
| `MANDAT_JOURNAL_ANCHOR_REKOR_PUBKEY` | открытый ключ журнала Rekor (PEM): им проверяется подпись checkpoint, к корню которого сходится доказательство включения |
| `MANDAT_JOURNAL_ANCHOR_POLICY` | `warn` (по умолчанию) или `fail`: в pilot/prod без якоря `mandat serve` не стартует |

Закрытые сегменты перечислены в манифесте `<журнал>.segments` (SHA-256 и диапазон записей каждого). Квитанции лежат рядом с журналом в `<журнал>.anchors`; `mandat journal-verify` с заданным `MANDAT_JOURNAL_ANCHOR` требует квитанцию на каждый закрытый сегмент и перепроверяет её у приёмника. Публичный Rekor раскрывает хеши и время записи, но не содержимое журнала.
