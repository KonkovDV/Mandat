# Границы утверждений

Где проходит граница стенда и что к ней добавляет пилот. Логика проверки, мониторинг, журнал и удостоверения работают и покрыты тестами. Внешние источники подключены через порты: реестр МЧД, ЕГРЮЛ (Единый государственный реестр юридических лиц) и ЕФРСБ (Единый федеральный реестр сведений о банкротстве) на стенде берут данные из кейса, подпись КЭП (квалифицированная электронная подпись) ждёт СКЗИ банка, правила ждут утверждения юристом. Большинство пунктов ниже закрывается шагом пилота без переделки ядра.

Каждый отчёт показывает то же самое в плашке «Режим стенда». Цифры и их границы — в [реестре утверждений](CLAIMS_REGISTRY.md), ступени готовности — в [docs/audit/READINESS_GATES.md](docs/audit/READINESS_GATES.md).

## Данные

- Все документы, ИНН, ОГРН и СНИЛС в демо сгенерированы. Контрольные числа верны, но организации и люди вымышлены. Документы реальных клиентов в разработке не использовались.
- Коды полномочий синтетические (`SYN-…`). Банковских кодов классификатора в открытых источниках мы не нашли и не придумываем их. Импорт из выгрузки ЕСНСИ (Единая система нормативной справочной информации) готов (`scripts/import_classifier.py`), коды выбирает банк.
- Снимок классификатора ФНС (kpmp.nalog.gov.ru) импортируется из файла, сервис не вызывается; на прошлую дату сервис справочник не отдаёт, поэтому старые операции проверяются только по снимку того времени. Снимок старше операции больше чем на `MANDAT_CLASSIFIER_MAX_AGE_DAYS` (по умолчанию 3 дня, не из норм) и неоднозначный код ведут к разбору человеком ([CLASSIFIER](docs/CLASSIFIER.md)).

## Формат МЧД

- Пути полей сверены с XSD (XML-схема, задающая формат файла) `EMCHD_1` по двум совпадающим открытым копиям. Официальной публикации ФНС мы не нашли, сама схема в репозиторий не входит ([формат](docs/FORMAT_NOTES.md)).
- Нотариальное удостоверение передоверия читается, но по реестру нотариусов не сверяется.
- Формы Банка России и нотариальные МЧД по 315-ФЗ пока только заготовлены в реестре форматов.
- Сканы бумажных доверенностей не распознаются, такие кейсы идут на разбор.

## Внешние системы

- Реестр МЧД и ЕГРЮЛ: на стенде — данные из пакета кейса, адаптеры банка подключаются на пилоте. Нет записи — ответ «недостаточно данных», а не «действует».
- Подпись КЭП: порт есть, но без СКЗИ (средство криптографической защиты информации) банка статус всегда «не проверено». В профиле `demo` эта проверка снята, в `strict` она обязательна, и без неё «подтверждено» не бывает.
- ЕФРСБ не подключён. Банкротство берётся из поля кейса; нет записи — «не проверено», а не «банкротства нет». Какие процедуры прекращают доверенность, должен подтвердить юрист ([нормы](docs/REGULATORY.md#банкротство)).
- С ДБО (дистанционное банковское обслуживание, интернет-банк), антифродом, ФинЦЕРТ и СЭД (система электронного документооборота) банка интеграции нет. Роль только рекомендуется; мониторинг меняет статус удостоверений «Мандата», а не права в интернет-банке.

## Правила и качество

- Все 39 правил — черновики (`draft`): норма указана, юрист банка их не утверждал. Окно «свежей» смены руководителя (30 дней) и допустимую длину цепочки калибрует банк.
- Цифры синтетического корпуса показывают, что правила срабатывают на заложенные нами дефекты. Точность на реальном потоке они не измеряют ([оценка](docs/EVALUATION.md)).
- Ссылка R-ID-003 на приказ Росфинмониторинга № 74 (п. 8) сверена по реквизитам и тексту; применимость к банку в сценарии Mandat юрист не подтверждал (M-07, [LEGAL_REVIEW](docs/LEGAL_REVIEW.md#11-приказ-росфинмониторинга--74)).
- Сроки разбора (SLA) по умолчанию — P1 4 ч, P2 24 ч, P3 72 ч — не из норм; реальные значения задаёт банк ([REVIEW](docs/REVIEW.md#sla)). Сроки задаются в `MANDAT_REVIEW_SLA_HOURS`; просрочка поднимает приоритет в ответах API, но уведомлений нет. Разбор человеком (M-09) доступен через API (`/v1/cases/{id}/review`, `/v1/review/queue`), ограничения — в [REVIEW](docs/REVIEW.md#ограничения).
- Свойство «передоверие не расширяет полномочия» проверено перебором 384 цепочек, а не доказано для любых входов.
- Ограничения устава ищутся шаблонами типовых формулировок. Нетиповой устав идёт на разбор. Для операции, где устав обязателен, найденный фрагмент не закрывает остальной текст: без отметки demo «ограничений нет» это «на разбор», не «подтверждено» (R-CHR-002).
- Два разных передоверия от одной МЧД в один день (разный sha256) правило не выбирает: R-SUB-009 даёт «на разбор». Тот же документ (тот же sha256) повтором не считается. Норма, какое из соседних передоверий действует, не утверждена.
- Нет признака совместных полномочий (ПрСовмПолн) — «на разбор», даже если в МЧД назван один представитель (R-JNT-001). Явное «не совместно» по-прежнему не требует второго подписанта.
- Снимок реестра, снятый после даты операции, в котором МЧД отменена или истекла, но дата события не указана, не доказывает прекращение к дате операции: R-REG-001 даёт «на разбор», каскад R-SUB-006 не срабатывает. Снимок без момента запроса и без даты события по-прежнему опровергает. Это не модель добросовестности третьего лица по ст. 189 ГК РФ.
- Требования Банка России к банкам при смене руководителя (Инструкция № 204-И, Положение № 499-П) по первоисточникам не проверены и в правила не заложены.

## Безопасность и защита данных

- Оценку соответствия 152-ФЗ и аттестацию проект не проходил.
- Журнал решений защищён хеш-цепочкой и HMAC (контрольной подписью журнала на секретном ключе). Корень дерева Меркла (одна контрольная сумма всего журнала, по которой можно доказать наличие отдельной записи) сам никуда не публикуется: его нужно выгружать и сверять командой `journal-verify --merkle-anchor`. При `MANDAT_ENV=pilot` или `prod` без ключа журнал не пишется. Файл блокировки хранит pid писателя и снимается только если этот процесс точно мёртв; по возрасту файла блокировка не снимается. Пустой файл и pid, который нельзя проверить, ждут до 5 с и дают «журнал занят». Повторное использование номера процесса между проверкой и снятием остаётся теоретическим окном.
- Удостоверения и списки статусов подписаны Ed25519 по образцу стандарта W3C Data Integrity (W3C — консорциум веб-стандартов). С внешними верификаторами совместимость не проверялась, переход на ГОСТ-подпись — задача пилота.
- Списки статусов удостоверений (**StatusRegistry**): один узел под `fcntl.flock` (CAS sequence, OR только для revocation); multi-replica writers без общего lock/store не поддерживаются. Модуль делает `import fcntl` на верхнем уровне — **только POSIX/Linux** (Docker/WSL). На native Windows импорт падает (`ImportError`), поэтому status + `attest-verify` с каталогом статусов там не работают; для демо на Windows используйте Docker/WSL. CI Windows matrix нет.
- `MANDAT_ENV=pilot` сам по себе не делает развёртывание пилотом. `deploy/compose.pilot.yml` + `/readyz` проверяют конфигурацию (том, журнал, хранилище, ключи) и перезапуск контейнера в CI; они не дают внешнего якоря, резервных копий, TLS, ротации ключей и не делают запись журнала и хранилища одной транзакцией (M-10: не exactly-once, см. абзац ниже). Ничего здесь не означает exactly-once.
- Журнал и хранилище (M-10): `POST /v1/cases` пишет в три шага — stage в хранилище, запись журнала, commit; отчёт виден и ответ 200 уходит только после commit. После сбоя между шагами сверка (при старте и при повторе по тому же кейсу) подтверждает отчёт, если в журнале есть запись этой попытки, и отбрасывает, если нет. `Idempotency-Key` (на 24 часа, на пользователя) возвращает прежний результат и не пишет вторую запись журнала. Номер попытки (fencing) не даёт вытесненной попытке подтвердить отчёт. Это НЕ распределённая транзакция и НЕ exactly-once: журнал и хранилище остаются двумя системами; вытесненная по сроку заявки (30 с) медленная попытка может оставить запись журнала без отчёта; повтор без `Idempotency-Key` после сбоя получает 409, а `replace=true` честно пишет вторую запись. Другие маршруты записи журнала (review и т. д.) этой схемой не охвачены.
- Авария списка статусов (outage): в pilot/prod без свежего списка / без high-watermark `seen` допуск операции fail-closed; «продолжать по кэшу после отзыва» не поддерживается. Окно свежести по risk — `status_max_age_for` / CLI `--operation-risk`. Глобальный `MANDAT_STATUS_MAX_AGE_DAYS` берётся как min с окном risk-tier и ослабить payment/high не может (G1). В pilot/prod JSON `MANDAT_STATUS_MAX_AGE_BY_RISK` может только ужесточить defaults (G-A; `{"payment":3650}` → ошибка). В pilot/prod незаданный `operation_risk` (None/пусто) — самое строгое окно из карты, а не 7 дней (G-B); явный `default` = 7 дней. На стенде None = `default`. **Ломающее изменение для интеграторов:** `check_status` / `validate_attestation` / `authorize_operation` без `operation_risk` в pilot/prod теперь получают строжайшее окно (на уровне payment, по умолчанию менее суток) и могут вернуть «список устарел» там, где раньше проходили; передавайте `operation_risk` явно. Второе: в pilot/prod `check_status` без `now` не возвращает «действует» — состояние «свежесть не проверена». Отзыв и приостановка сообщаются и без `now`. На стенде (demo, dev, test) без `now` список без отзыва по-прежнему «действует».
- Привязка к запросу (M-04): удостоверение подписывает сумму, псевдоним представителя, получателя (`audience`) и одноразовый `nonce`; `authorize_operation` сверяет их с `OperationRequest`. Хранилище использованных nonce «Мандат» не ведёт: его передаёт интегратор функцией `consume_nonce`, и защита от повтора держится на ней; для нескольких реплик нужно общее атомарное хранилище. **Ломающее изменение для интеграторов:** в pilot/prod `authorize_operation` без `request`, `pseudonym_key` и `consume_nonce` возвращает отказ.
- Токены API (M-12): срок (`expires_at`) и отзыв (`revoked`) проверяются при каждом запросе в ЛЮБОМ режиме, если поля заданы. Обязательность `expires_at` и потолок срока 366 дней от загрузки списка действуют только в pilot/prod (и любом защищённом режиме). Общий `MANDAT_API_TOKEN` (режим стенда) срока жизни не имеет. Отзыв без рестарта работает только если `MANDAT_API_USERS` — путь к файлу, файл обновляется атомарно (tmp + rename), и только на одном хосте (общего реестра токенов между репликами нет). Часы сервера считаются точными (допуска на расхождение нет). Ротация — организационный процесс (docs/KEYS.md). Это не OIDC и не сессии.
- CLI `attest-verify --status-dir` вызывает `check_status(require_seen=False)`: это диагностика статуса, а не допуск операции; high-watermark `seen` обязателен только в `authorize_operation`.
- Ключи лежат в файлах с правами 0600 (в Windows права POSIX (стандарт Unix-систем) не действуют). Для пилота нужен KMS (сервис управления ключами) или HSM (аппаратный модуль для хранения ключей) банка.
- Событие мониторинга подписывается только при заданном `MANDAT_WEBHOOK_SECRET`; доставки в антифрод нет.

## Модель

- Языковая модель по умолчанию выключена. Качество и лицензия on-prem модели на уставах не проверялись.
- Псевдонимизация не обезличивание: текст для модели остаётся персональными данными. В модель уходят только строки устава о полномочиях; ФИО людей из данных кейса (ЕГРЮЛ, МЧД, заявка) заменяются меткой роли во всех падежах и с инициалами; дата рождения и адрес человека вырезаются по подписям и шаблонам, адрес юридического лица остаётся. Остальные ФИО заменяются меткой `[ФИО]` по словарю имён и фамилий Wikidata (CC0) и правилам соседства (`privacy/unknown_names.py`); на синтетической выборке полнота по людям 98,1 % (95 % ДИ 95,7–99,4 %) на фамилиях не из словаря. **Остаточный риск:** одиночная фамилия без имени, отчества и инициалов, которой нет в словаре и у которой нет русского суффикса («по заявлению Шор»), уходит в модель как есть (на выборке ловится 25 из 30, ДИ 65–94 %); склонение по правилам, не по морфологическому словарю; распознавание проверено на синтетике, не на документах банка ([DATA_PROTECTION](docs/DATA_PROTECTION.md#псевдонимизация--не-обезличивание)).
