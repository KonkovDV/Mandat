# История изменений

Последний релиз — 0.4.0, к полуфиналу: подписанные файлы и образ контейнера лежат на [странице релиза](https://github.com/KonkovDV/Mandat/releases/tag/v0.4.0). Числа о продукте на каждый момент — в `evidence.json`.

## Не выпущено

### Ёмкость и поток на 100 000 пакетов (28.11.2026)

- Поток пакетов по профилю банка (`python -m mandat.eval.synth`, `python -m mandat.eval.run`, профили в `data/load_profiles.json`) и нагрузка `scripts/load_test.py`: узел 4 vCPU держит до 239 проверок пакета и до 230 допусков ДБО в секунду, расчёт узлов и план роста — в [ёмкости](docs/CAPACITY.md).
- Поток на 100 000 пакетов поймал случай с часовым поясом в R-REG-001: снимок реестра датировался днём в поясе записи, а не днём по Москве. Правило переводит момент запроса в Europe/Moscow, регрессионный тест держит один вердикт для `+03:00`, `+10:00`, `-05:00` и `Z`; повторный прогон — 100 % совпадений и ноль ложных «подтверждено».
- Горячий путь ускорен без изменения решений: допуск ×14–31 по пропускной способности, ошибок под нагрузкой — ноль, решения те же байт в байт (`tests/test_hot_path_caches.py`).
- `evidence.json` несёт раздел `repeat_clients`: с реестром заключений юриста к человеку идут 47 из 100 платежей повторных клиентов вместо 100 (C-27).
- nginx стенда: тяжёлые действия (модель, прогон, шлюз) — 30 запросов в минуту с адреса и всплеск 20, жюри за одним NAT не упирается в лимит.

### Консультант на OpenRouter (28.11.2026)

- Пять недорогих моделей прошли один замер на уставах и демо-кейсах ([замер](docs/ADVISORY_MODELS.md)): лишних фактов ноль у всех. Стенд работает на `mistralai/mistral-small-3.2-24b-instruct` — открытые веса Apache-2.0, та же модель ставится в контур банка, 96 % фраз пояснения проходят фильтр; самый быстрый вариант через API — `deepseek/deepseek-v4-flash`.
- Пояснение сотруднику — две–четыре фразы: вердикт с главной причиной и шаг словами отчёта. Фильтр пояснений проходят 93–96 % фраз против 78–85 % раньше, ответ короче и дешевле.
- Замер записывает результат после каждой модели и ограничивает время вызова (`--timeout`): медленный провайдер не задерживает остальные модели.

### MCP для ИИ-агентов (28.11.2026)

- `mandat mcp` — «Мандат» по Model Context Protocol (stdio, версия 2025-06-18) для ИИ-агентов банка: `check_authority` проверяет кейс тем же движком, что `POST /v1/cases`, `admit_operation` допускает операцию по удостоверению тем же кодом, что AuthZEN, `get_report` отдаёт отчёт только своей сессии ([MCP](docs/MCP.md)).
- Агент работает от учётной записи API по токену `MANDAT_MCP_TOKEN`: роль и `audiences` решают, как в HTTP, каждый вызов пишется в журнал аудита с `via: mcp`, `nonce` общий с HTTP.
- Допуск операции собран в `services.admission.admit`, профиль AuthZEN читает обычный JSON без FastAPI: HTTP, AuthZEN и MCP идут одним путём решения.

### Расход модели и эксплуатация стенда (28.11.2026)

- Консультант: предохранитель — после трёх неудач подряд (сеть, тайм-аут, ответ не JSON, ни одного факта через шлюз, ответ позже 8 секунд) модель на паузе 120 секунд, пояснение сразу собирается из фактов отчёта, затем один пробный вызов. Дневной бюджет по `usage.cost` провайдера, по умолчанию 1 $ за день по Москве: после потолка до полуночи отвечают только правила, и консоль так и пишет. Кэш ответов, которые шлюз принял целиком, по SHA-256 обезличенного запроса и модели: 256 записей, сутки. Настройки — `MANDAT_LLM_BREAKER_*`, `MANDAT_LLM_BUDGET_USD_PER_DAY`, `MANDAT_LLM_CACHE_*`, их читает только `advisory/llm.py`.
- Счётчики модели — вызовы, неудачи, открытия предохранителя, попадания в кэш, токены, расход и остаток бюджета — в блоке «Расход модели» на вкладке «Прогон» (`/console/api/stats`) и в `/health` стенда; ключа, запросов и ПДн в них нет.
- Цитата из ответа модели сверяется и с обезличенным текстом, который модель получила; устав со словами из кириллицы и латиницы вперемешку даёт пояснение, а не ошибку сервера.
- `mandat backup`: копия каталога данных без остановки службы — журнал аудита под его блокировкой записи с проверкой копии, базы SQLite их собственным резервным копированием, остальные файлы атомарно; `MANIFEST.json` с SHA-256 и ротация последних копий.
- `scripts/deploy_stand.sh`: часовой пояс Москвы, swap на машине меньше 2 ГБ, потолок journald, сторож здоровья службы раз в минуту, копия данных в 03:15 МСК (14 копий), fail2ban для sshd, потока сверх лимитов nginx и подбора токена API, автоматические обновления безопасности. В настройки модели стенда добавлены `MANDAT_LLM_EXTRA` (провайдеры без хранения запросов, стоимость в ответе) и дневной бюджет; модель по умолчанию — `mistralai/mistral-small-3.2-24b-instruct`, быстрее и дешевле — `deepseek/deepseek-v4-flash`. Всё описано в [стенде](docs/STAND.md).

### Реестр заключений юриста по уставам (28.11.2026)

- Юрист читает устав один раз на редакцию: заключение привязано к ОГРН клиента и sha256 документа устава, у него вывод, основание, область (операции и предел суммы), автор, утвердивший и срок ([реестр заключений](docs/CONCLUSIONS.md)).
- Четыре глаза: черновик пишет оператор или сотрудник разбора, утверждает только юрист и только не автор; отзыв — юрист с причиной.
- Строгий профиль применяет утверждённое действующее заключение по той же редакции, и R-CHR-002 называет его номер, утвердившего, дату и основание. Ограничение из заключения проверяет R-CHR-001, а не гасит. Другая редакция, истёкший срок, отзыв или операция вне области — разбор с причиной; профиль demo не изменился.
- Проект заключения по кейсу готовит модель банка через шлюз цитаты, без модели проект пуст; действует он только после подтверждения автором и утверждения вторым юристом.
- Новая редакция устава ставит прежнее заключение на перепроверку, а разбор кейса показывает юристу, какое заключение действовало.
- Каждый шаг и каждое применение — в журнале аудита; заключения лежат в хранилище API (память, SQLite, Redis, с шифрованием по `MANDAT_STORE_KEY`), список показывает число применений.
- `mandat eval` и `mandat showcase` считают повторных клиентов: без реестра к юристу уходят 100 платежей из 100, с реестром — 47, ложных «подтверждено» нет. Вкладка «Юрист» консоли стенда показывает реестр демо-клиента и применение заключения в проверке.

### Тексты для жюри и план пилота (28.11.2026)

- Тексты говорят, что работает на стенде и что подключает банк: для ДБО готов контракт допуска и сценарий на стенде, ядро рассчитано на контур банка, проверка кейса — медиана 3,9 мс и 95 % быстрее 5,6 мс, подпись подключается к HSM банка по PKCS#11 или Vault. Утверждение о работе в контуре банка в настоящем времени добавлено в запрещённые формулировки.
- Экономика: «Мандат» обходится банку около 69 ₽ на проверку, ручная проверка сегодня — около 540 ₽; 75 ставок — объём ручной работы, долю, которую снимает «Мандат», меряет пилот. В [экономике](docs/ECONOMICS.md) — бюджет пилота и рычаги NPV базового сценария.
- Пилот: 4–8 недель подготовки, выборка от 300 пакетов, метрики успеха и владелец каждого стыка; теневой пилот идёт в строгом профиле ([пилот](docs/PILOT.md)).
- Пилотный compose без внешнего якоря журнала не стартует: `MANDAT_JOURNAL_ANCHOR_POLICY=fail` по умолчанию.
- Схема EMCHD_1 сверена по открытой копии с записанным sha256; обзор открытого кода называет библиотеки, стандарты и вендоров.

### Исправления по red-team (28.11.2026)

- Допуск операции: окно свежести списка статусов задаёт подписанная операция и каталог операций, `operation_risk` его только сужает; уровень не из карты окон — 422, в AuthZEN — 400.
- Хранилище API: квота отчётов — на пользователя; кейс в разборе не вытесняется, вытеснение пишется в журнал (`evict_case`), при полной квоте — 429; очередь не прячет кейс без отчёта.
- ФИО перед моделью: заглавные, латинские буквы-двойники и разрядка выравниваются до поиска; текст со словом из кириллицы и латиницы вперемешку в модель не уходит.
- Манифест: две записи реестра или формы передоверия для одной МЧД, которые различаются только написанием номера, — ошибка кейса.
- R-ID-003: если МЧД пакета не разобрана, отсутствие заявителя в остальных — «не проверено», а не отказ. R-EIO-006: выписка ЕГРЮЛ, датированная позже момента проверки, не принимается.
- Разбор: `reviewer` видит чужой кейс, пока он в разборе или если уже действовал по нему. Журнал сервера для `POST /v1/events` пишет тип ошибки и путь поля без значений клиента.
- Устав: «подписываются двумя лицами», «за подписью двух должностных лиц» — совместная подпись.

### Конкуренты с открытым кодом, стандарты и чек-лист перед пилотом (24.11.2026)

- Изучен открытый код по МЧД и проверке полномочий на GitHub ([конкуренты](docs/COMPETITORS.md#открытый-код-на-github)): Библиотека стандартных подсистем 1С, клиенты и разборщики МЧД, Ballerine, Marble, AuthZEN и Cerbos, Catala и OpenFisca, Biscuit, GLEIF vLEI, правила удостоверений европейского пилота WE BUILD, AP2. Вывод тот же: решения «вправе ли этот человек провести эту операцию за эту компанию в этот день» с ЕГРЮЛ и уставом в найденном коде нет.
- МЧД за подписью нескольких лиц без доверенности. В XSD EMCHD_1 у `ЛицоБезДов` `maxOccurs="unbounded"`, а разбор отвергал такой документ как повтор элемента и просил у клиента «читаемую МЧД». Теперь каждое лицо читается, R-EIO-001 сверяет с ЕГРЮЛ каждого, а руководителя, который МЧД не подписал, отдаёт на разбор: совместно или независимо действуют руководители, решает устав (п. 3 ст. 53 ГК РФ). Так закрыт путь к ложному «подтверждено»: два руководителя в ЕГРЮЛ, подпись одного, устав не приложен. Остальные правила, маскировка ФИО перед моделью и карточка видят всех подписантов; у МЧД с одним подписантом ссылки и хеш отчёта прежние. 19 тестов, документы с двумя лицами проходят XSD.
- Допуск операции по OpenID AuthZEN Authorization API 1.0 (финальная спецификация от 12.01.2026): `/.well-known/authzen-configuration`, `/access/v1/evaluation` и `/access/v1/evaluations` с тремя семантиками пакета. Решение считает та же функция, что у `/v1/operations/authorize`; отказ — 200 с причинами, ошибка запроса — 400 без расхода `nonce`, ошибка одной оценки пакета — в её `context.error`. Поиска (раздел 8) нет: точка решений без состояния не знает, кто ещё вправе действовать. 47 тестов по разделам спецификации ([запуск](docs/RUN.md#допуск-по-openid-authzen-10)).
- Весь API возвращает присланный `X-Request-ID`, если он из безопасного алфавита (в журнал сервера — через маску номеров), и отвечает на 401 с `WWW-Authenticate: Bearer` по RFC 6750.
- Воркшоп Академии Финтеха 20.11.2026 «Данные, безопасность и комплаенс» разложен на код ([чек-лист перед пилотом](docs/PILOT_CHECKLIST.md)): у каждого поля ПДн названа цель, у каждого маршрута — данные и получатель, у каждой копии — срок и удаление; матрицы применимости и готовности. Статус «проверено» ставит прогон тестов пункта при сборке `evidence.json`, пункты банка — «не проверено» с владельцем и условием допуска. Тест не даст добавить сетевой модуль без маршрута в карте и поле ПДн без цели.
- Основание решения разбора уходит в журнал аудита отпечатком HMAC на ключе журнала, а не текстом. Документы обещали «в журнале только хеши и идентификаторы», а свободный текст сотрудника, где бывает фамилия клиента, ложился в журнал, который не стирается. Текст остаётся в истории разбора и удаляется вместе с кейсом.
- `mandat restore-check`: после восстановления хранилища и списков статусов из копии журнал служит опорой. Удалённый по 152-ФЗ после снятия копии кейс удаляется снова вместе с историей разбора, отзыв из журнала снова выставляется в списке, нечитаемая запись — нарушение; починка пишется в журнал. Копирование ещё не значит восстановление (NIST SP 800-53, CP-9 и CP-10).
- `mandat incident-report`: сроки по ч. 3.1 ст. 21 152-ФЗ — оба от выявления, 24 и 72 часа, а не 24 + 72; кто, сколько раз и сколько кейсов создавал, читал и удалял — из журнала, только если он цел.
- `mandat access-review` и необязательное поле `owner` у учётной записи API (`mandat api-user --owner`): ревизия называет записи без срока, с долгим сроком и без владельца отзыва — чтобы временный доступ подрядчика не пережил работу.
- Матрица доступа одним тестом: шесть ролей на каждом пути к кейсу, чужой кейс отвечает так же, как несуществующий (OWASP API Security Top 10 2023, API1).
- Нормы о защите данных: ответ воркшопа на вопрос о проекте 169583 — на 19.11.2026 это проект, а не действующий акт; ориентир — действующий приказ ФСТЭК № 21, статус проверяется на дату запуска. SOTA: AuthZEN, Biscuit и UCAN, карта соответствия с WE BUILD; SD-JWT VC (draft-26 в IESG) и Token Status List (очередь RFC Editor) по-прежнему ждут RFC.

- Ключи в pilot и prod — только случайные. Ключи журнала, ПДн и хранилища и общий токен стенда теперь должны быть не меньше 32 байт в hex или base64, как дают `openssl rand -hex 32` и `secrets.token_urlsafe(48)`; пароли, повторы вроде `kkkk…` и короткие ключи сервис не принимает. HKDF и HMAC перебор не замедляют, а по ключу ПДн и маленькому пространству ИНН восстанавливается ИНН. Вывод ключа не изменился, записи под прежним случайным ключом читаются; с ключа-пароля уходят через `MANDAT_STORE_KEY_PREVIOUS`.
- Поиск адресов почты при псевдонимизации был квадратичным: устав со строкой «a.a.a…» на 100 000 знаков разбирался 30 с. Теперь поиск идёт от каждого «@» за один проход и находит ровно то же, что прежнее выражение (сверено на 30 000 случайных строк): 0,02 с. Маска журнала сервера обрезала текст после маски, и причина ошибки с мегабайтом ввода держала процесс часами; теперь обрезка до маски с запасом, а номер на границе всё равно скрыт.
- Мониторинг выдерживает тяжёлые пачки. Окно захвата раньше перебиралось заново для каждого события: 20 тысяч событий одной компании считались 23 с, а пачка в 8 МБ держала процесс минуты. Теперь окно скользит за один проход и совпадает с прежним перебором на 300 случайных пачках, права ищутся по номеру МЧД, сроки — по индексу цепочки; 8 МБ — 0,3 с. Повторная доставка того же события тревоги не дублирует, а ответ ограничен миллионом связей «тревога — право»: сверх — 422 с советом разбить пачку по организациям.
- Напоминание уже в коде. У выданного права может быть последний день действия каждой МЧД цепочки (`poa_valid_until`). За 30 дней до конца срока `mandat monitor` и `POST /v1/events` поднимают тревогу `poa_expiring`; срок права — самый ранний в цепочке, потому что передоверие не живёт дольше основной МЧД (п. 4 ст. 187 ГК РФ). Если срок прошёл, а события реестра не было, удостоверения отзываются, как по `POA_EXPIRED` (подп. 1 п. 1 ст. 188 ГК РФ). Момент проверки — `--as-of` или `as_of` в пачке, дни считаются по московскому календарю. Пример — `examples/events/poa_expiring.json`, 19 тестов.

### Допуск операции и захват компании

- `POST /v1/operations/authorize`: ДБО получает допуск одной операции по удостоверению «Мандата». Допуск сверяет организацию, день операции по Москве, операцию, сумму, представителя, получателя и одноразовый `nonce` ([RUN](docs/RUN.md#допуск-операции-для-дбо)).
- `nonce` расходуется атомарно: из одновременных повторов проходит один, повтор после потерянного ответа получает отказ с временем первого допуска (`already_admitted`), откат списка статусов — отказ. Сбой хранилища во время допуска не оставляет «уже допущен» без допуска.
- Допуск в `pilot` и `prod` получает только служебная учётная запись системы банка (`dbo`) со своим списком получателей.
- Срок удостоверения не длиннее 30 дней и сроков документов цепочки. Смена руководителя отзывает удостоверения руководителя, который действовал без МЧД.
- `mandat showcase` одной командой проводит сценарий захвата: допуск платежа, отказ повтору и завышенной сумме, признаки захвата и отказ следующему платежу до списания денег.

### Правила и нормы

- Правило утверждает только подписанная запись юриста с хешем текста правила, а для правил, которые читают каталог операций, — и с хешем каталога. Строка `approved` в `rules.json` статус не меняет ([ADR-009](docs/adr/ADR-009-rule-approval-records.md)).
- Карточка нормы на каждое правило для юриста банка ([пакет для юриста](docs/legal/README.md)). Приказы Минцифры № 857, № 1001 и № 856 прочитаны по официальному опубликованию, у пяти правил есть дословные цитаты.
- R-FMT-003 сверяет реквизиты МЧД по редакции требований на дату выдачи.
- Пакет правил хранит сроки актов: с 01.09.2027 (315-ФЗ) R-FMT-002 принимает МЧД только в формах из списка банка, с 27.07.2027 (253-ФЗ) R-EIO-004 объясняет реструктуризацию долгов юрлица, правила на приказах № 856 и № 857 после 01.03.2028 «подтверждено» не дают, пока пакет не пересверят. Ближайшие даты показывает `mandat law-calendar` ([ADR-010](docs/adr/ADR-010-norm-validity.md)).
- «Подтверждено» не ставится, когда обязательный устав разобран только частично (R-CHR-002), от одной МЧД в один день выданы разные передоверия (R-SUB-009), в МЧД нет признака совместных полномочий (R-JNT-001), у кода полномочия нет даты начала (R-COV-002) или реестр опрошен после даты операции без даты отмены (R-REG-001).
- Форма передоверия (R-SUB-010) экспортируется в Cedar и сверяется со второй реализацией.
- Порт реестра МЧД ищет доверенность по номеру и двум ИНН, как реестр ФНС с 01.03.2026.
- У манифеста кейса есть JSON Schema. Поле вне контракта вне стенда — ошибка входа.
- Требования Банка России при смене лиц с правом подписи (Инструкция № 204-И, Положение № 499-П) прочитаны по тексту и описаны в [границах](LIMITS.md).

### Защита данных

- Каждое чтение отчёта с персональными данными, включая повтор по `Idempotency-Key`, пишется в журнал. Без журнала отчёт не выдаётся.
- Кейс с персональными данными удаляется по основанию из 152-ФЗ, удаление записано в журнале без самих данных, а запись затирается в файле базы.
- Отчёты и разборы лежат в хранилище зашифрованными (AES-256-GCM, `MANDAT_STORE_KEY`). Шифр привязан к виду записи, кейсу и владельцу, подмена записи обнаруживается.
- Журнал сервера маскирует номера, записанные группами, и номера в пути запроса.
- Перед моделью ФИО из кейса заменяются ролью, незнакомые фамилии ловятся по соседним словам и словарю, дата рождения и адрес вырезаются, номера становятся псевдонимами с проверкой контрольных чисел.
- Карта применимых норм о защите данных и того, как они закрыты ([нормы о защите данных](docs/DATA_PROTECTION_LAW.md)).
